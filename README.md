## 설치

1. Chrome 주소창에 `chrome://extensions` 입력
2. 우측 상단 **개발자 모드** 켜기
3. **압축해제된 확장 프로그램을 로드합니다** 클릭
4. `C:\Users\admin\workspace\kny\mango\order-details\extension` 폴더 선택

> 이미 설치되어 있다면 `chrome://extensions` 에서 **새로고침(⟳)** 을 누른 뒤
> 마켓·망고 탭을 각각 새로고침해야 변경이 반영된다.

### 계정이 여러 브라우저에 흩어져 있다면 (릴레이)

무신사 계정이 셋이라 크롬·웨일·엣지에 하나씩 로그인해 두는 경우다. **확장은 브라우저마다
완전히 격리되어**, 웨일에 설치한 확장의 `chrome.tabs` 로는 크롬의 망고 탭을 볼 수 없다.
(크롬 프로필을 나눠도 마찬가지다.) 그래서 사이에 루프백 서버 하나를 둔다.

1. 세 브라우저 **모두**에 같은 `extension` 폴더를 로드한다
   - 웨일 `whale://extensions` · 엣지 `edge://extensions` — 둘 다 크로미움이라 그대로 붙는다
2. 릴레이를 띄운다 — 둘 중 하나
   - **로그온할 때 자동으로** (권장): `relay\install-startup.vbs` 를 더블클릭한다.
     시작프로그램에 등록되어 다음 로그온부터 **창 없이** 뜬다. 해제는 `uninstall-startup.vbs`.
   - **그때그때 손으로**: `relay\start.cmd` 를 더블클릭한다 (창을 닫으면 멈춘다).
3. 끝. 어느 브라우저가 보내는 쪽인지 **설정할 것이 없다.**

> 자동 실행은 **현재 사용자 로그온 시**로 등록된다 (관리자 권한 불필요).
> 등록되는 파일은 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\mango-relay.lnk`
> 하나뿐이고, 그게 `relay-hidden.vbs` → `run-hidden.cmd` → `node relay.js` 를 창 없이 띄운다.
> 창이 없으므로 로그는 `relay
elay.log` 에 쌓인다 (부팅마다 새로 쓴다).
> 폴더를 옮기면 바로가기가 끊기니 `install-startup.vbs` 를 다시 실행할 것.

   `수정하시겠습니까?` 확인창도 자동 승인되어 **저장까지 완료**된다

> 확장은 **이미 열려 있는 망고 탭에서만** 처리한다. 목록에 그 주문건이 없으면
> 값을 넣지 않고 그대로 멈춘다. 망고 탭을 대신 검색·이동시키지 않는다.

웨일·엣지처럼 **망고 탭이 없는 브라우저**에서 누르면, 값이 릴레이로 넘어가고
`넘겼습니다. 망고 탭이 열려 있는 크롬 창을 띄우면 반영됩니다` 라고 뜬다.
그 뒤 **크롬 창을 띄우는 순간** 크롬 쪽 확장이 가져가 반영·저장하고 알림을 띄운다.

## 주문건 매칭 방식

마켓의 **받는 분** 이름으로 망고 목록에서 후보를 찾고, 아래로 점수를 매겨 1건을 고른다.

- 이미 같은 주문번호가 들어있는 행 → 즉시 선택 (재전송)
- 총 결제금액 일치 (+4) / 같은 발주처 태그 (+2) / 상품주문번호 비어있음 (+1) / 상태가 결제완료 (+1)
- 반품·교환·취소완료 상태 (−5), 그리고 이 상태의 행은 값을 덮어쓰지 않고 중단

발주처 태그는 사이트 스크립트가 `marketTag` 로 넘긴다 — 롯데온은 `LOTTEON`, SSG는 `SSG.com`
(망고 목록 행에 `[SSG.com] 아이더 남성 …` 처럼 찍힌다). 문자열 대신 **배열**을 넘기면
그중 하나만 걸려도 인정한다 — 무신사는 표기를 확인하지 못해 `['무신사', 'MUSINSA']` 로 둔다.

목록 600건(12페이지)에 실제로 찍혀 있는 발주처 표기는 넷뿐이다 (2026-08-31 확인).

| 표기 | 건수 |
|---|---|
| `[LOTTEON.com]` | 308 |
| `[SSG.com]` | 175 |
| `[MUSINSA.com]` | 93 |
| `[FashionPlus.co.kr]` | 18 |

**전부 도메인 꼴**이다. 확인되지 않은 표기를 지어내 넘기면 점수는 못 얻으면서 후보 행마다
비교 비용만 붙으므로, 지마켓·패션플러스·롯데아이몰·더현대Hi·CJ온스타일·NS몰·GS SHOP·옥션·현대몰
은 태그를 넘기지 않는다.

동점 후보가 2건 이상이면 자동 입력하지 않고, 망고 화면에서 후보 행을 주황색으로 표시하고
**[여기에 적용]** 버튼을 띄운다.

## 안전장치

- 저장 직전 **모든 체크박스를 해제**한 뒤 대상 행만 체크한다 (선택수정이 다른 행까지 건드리는 것 방지)
- 동점 후보가 2건 이상이면 자동 입력·저장을 하지 않고 사용자에게 선택을 요구한다
- 반품/교환/취소완료 상태의 행은 값을 덮어쓰지 않고 중단한다

> 확인창 없이 바로 저장되므로 되돌리기가 없다. 매칭이 어긋나면 그대로 저장된다는 뜻이라,
> 위 세 가지가 유일한 방어선이다.

## 망고 페이지 성능

망고를 쓰는 동안 확장이 아무 부하도 주지 않도록, **망고 페이지에는 상주하는 코드가 없다.**

- `manifest.json` 의 `content_scripts` 는 마켓 주문상세 페이지에만 걸려 있다.
  망고 목록 페이지를 열고 검색하고 스크롤하는 동안 확장 코드는 한 줄도 실행되지 않고,
  CSS 도 주입되지 않는다.
- 마켓에서 전송 버튼을 누른 순간에만 `background.js` 가 `chrome.scripting.executeScript` 로
  `mango_main.js`(MAIN) 와 `mango.js`(ISOLATED) 를 주입하고 `__LM_MANGO__.run(payload)` 를 호출한다.
  두 스크립트 모두 자체 가드가 있어 재주입해도 한 번만 초기화된다.
- **그 주입도 문서당 한 번뿐이다.** 전송할 때 먼저 그냥 불러 보고, 이미 들어가 있으면 넣지
  않는다 (아래 '두 번째 전송부터는 주입하지 않는다' 절). 두 번째 전송부터 망고 페이지가
  받아서 파싱하는 바이트는 **0**이다.
- 후보 선택 UI 의 CSS 도 후보가 2건 이상일 때만 `<style>` 로 주입한다.

### 주입된 뒤의 스캔 비용

망고 목록 한 행은 **요소 345개 / `textContent` 3,896자**나 된다. 그중 절반(1,845자)은
트래킹번호 칸에 들어있는 `<style>` 블록과 택배사 `<select>` 옵션 목록인데, 매칭에는
전혀 쓰이지 않는다. 반면 **수령인 칸은 26자**뿐이다.

그래서 후보 판정을 두 단계로 나눈다.

1. **수령인 칸만** 읽어 거른다 — 행 전체의 1/150. 대부분의 행이 여기서 끝난다.
2. 살아남은 소수의 행만 결제금액·주문번호 칸을 마저 읽는다.

칸 위치는 헤더 텍스트(`수령인`, `결제금액`, `주문번호`)에서 한 번만 찾는다. 순서가 바뀌어도
따라가고, 못 찾으면 행 전체 텍스트로 폴백해 동작은 유지한다.

50행 목록에서 실측한 값 (Chrome, 50회 평균):

| 상황 | 기존 | 현재 |
|---|---|---|
| 일치 0건 (가장 흔함) | 0.89 ms | **0.056 ms** |
| 50행 전부 일치 (최악) | 1.01 ms | **0.25 ms** |

바꾸기 전후로 후보 목록과 점수가 완전히 같은 것을 같은 페이지에서 확인했다.

#### 행 목록을 문서가 아니라 **표에서** 얻는다 (2026-08-31 실측)

위 2단계 구조에는 낭비가 하나 남아 있었다. 1단계가 보는 건 **수령인 칸 하나**뿐인데,
행 목록을 만드느라 그 전에 이미 **체크박스 50개를 문서에서 찾아 각각 `closest('tr')` 로 행을
거슬러 올라가고 있었다.** 체크박스는 1단계를 통과한 소수의 행에만 필요하다.

그래서 `table.rows` 를 돌며 수령인 칸부터 읽고, 살아남은 행에서만 첫 칸의 체크박스를 집는다.
문서를 훑는 조회는 **표를 찾는 첫 체크박스 하나**로 줄었다.

| | 지금까지 | 바꾼 뒤 |
|---|---|---|
| `querySelectorAll('input.chklist[name="uid_check[]"]')` | 0.035 ms | — |
| `closest('tr')` 50번 | 0.012 ms | — |
| `querySelector` 첫 체크박스 하나 + `closest('table')` | — | 0.002 ms |
| `table.rows`(51행) 순회 | — | 0.007 ms |

| 상황 | 지금까지 | 바꾼 뒤 |
|---|---|---|
| 1건 일치 | 0.063 ms | **0.029 ms** |
| 0건 일치 (가장 흔함) | 0.057 ms | **0.026 ms** |
| 50행 전부 후보 (최악, 태그 없음) | 0.178 ms | **0.154 ms** |
| 50행 전부 후보 + 태그 1개 | 0.350 ms | **0.310 ms** |

후보가 많을수록 이득이 줄어드는 게 맞다 — 살아남은 행마다 체크박스를 집기 때문이다. 대신
**평상시(후보 0~1건)에 절반**이 된다.

**라이브 컬렉션인데 왜 괜찮은가.** 롯데아이몰 어댑터에서는 라이브 컬렉션이 *식었을 때* 튀는
것 때문에 일부러 피했다. 여기서 그 함정에 빠지지 않는 이유는 `table.rows` 를 다시 만드는 비용이
문서가 아니라 **그 표의 행 수**에 묶이기 때문이다. 문서를 훑는 라이브 컬렉션과 비교하면:

| | 캐시 따뜻할 때 | DOM 이 막 바뀐 직후 |
|---|---|---|
| `getElementsByName('uid_check[]')` | 0.0003 ms | **0.38 ms** |
| `getElementsByClassName('chklist')` | 0.0003 ms | **0.40 ms** |
| `querySelectorAll('input.chklist[name=…]')` | 0.035 ms | 0.029 ms (캐시 무관) |
| **행 스캔 전체 (`table.rows`, 1건 일치)** | **0.029 ms** | **0.031 ms** |

문서 전체를 훑는 라이브 컬렉션은 식으면 13배로 튄다. `table.rows` 는 식어도 0.002ms 늘 뿐이다.
(참고로 `[name="uid_check[]"]` 만으로 된 선택자는 클래스 인덱스를 못 써서 0.42ms 다 — 지금
선택자에 `.chklist` 가 붙어 있는 게 이 조회를 싸게 만들고 있었다.)

**체크 해제는 조금 비싸졌다.** 예전에는 스캔이 모아 둔 체크박스 목록을 그대로 재사용했는데
(0.003 ms), 이제 그 목록이 없어 `table.rows` 를 돌며 첫 칸에서 집는다 (**0.013 ms**).
문서 조회로 다시 모으면 0.026~0.028 ms 라 이쪽이 싸고, **매칭에 실패한 전송에서는 아예 돌지
않는다.** 스캔에서 아낀 0.031 ms 가 더 크다.

후보 목록·점수·체크 해제 결과가 바꾸기 전과 완전히 같은 것을 같은 페이지에서 확인했다
(payload 5종 — 1건 일치 / 0건 / 50행 전부 / 태그 있음 / 결제금액 불일치).

#### [선택수정] 버튼은 문서당 한 번만 찾는다 (2026-08-31 실측)

`[onclick*="really_all_select_modify"]` 는 인덱스를 못 쓰는 선택자라 문서를 통째로 훑는다
(0.0153 ms). 그런데 그 버튼은 목록을 다시 그리지 않는 한 그대로 있고, 목록을 새로 검색하면
페이지가 통째로 바뀌어 캐시도 같이 사라진다. 그래서 찾은 요소를 들고 있다가 `isConnected` 로만
확인한다 — 주문건을 연달아 보낼 때 매번 내던 비용이 두 번째 전송부터 사라진다.

그 **첫 번째 한 번**도 뒤에 다시 줄였다 (아래 '[선택수정] 버튼을 클래스로 먼저 좁힌다' 참고) —
0.0153 → 0.0072 ms.

#### 두 번째 전송부터는 주입하지 않는다 (2026-08-31 실측)

위 표에 **없던 줄**이 하나 있었다. 이 파일은 오랫동안 스캔·쓰기·체크 해제만 재고 있었는데,
정작 전송 한 번에 망고가 쓰는 시간의 **절반**은 그 앞에 있었다 — `mango.js`(21,678바이트)와
`mango_main.js`(531바이트)를 **매번 다시 넣는 비용**이다.

두 파일에는 자체 가드가 있어(`if (window.__LM_MANGO__) return;`) **실행**은 즉시 되돌아
나온다. 그래서 공짜인 줄 알았는데, 그 전에 망고 페이지가 22KB 를 받아 **파싱은 다 한다.**
실제 목록(요소 17,069 · 클릭요소 2,477)에서 같은 크기·같은 모양의 소스를 넣어 재 봤다.

| 문서에 스크립트를 다시 넣는 비용 | 중앙값 | 최악 |
|---|---|---|
| 빈 스크립트 (요소 생성·삽입 자체) | 0.002 ms | 0.003 ms |
| `mango_main.js` 크기 (531B) | 0.012 ms | 0.0145 ms |
| `mango.js` 크기 (21,678B) | 0.031 ms | 0.149 ms |
| **합** | **0.043 ms** | **0.164 ms** |

(200개씩 묶어 15시행 중앙값. `performance.now()` 분해능이 0.1ms 라 한 번씩 재면 전부 0이
나온다 — 묶어서 재야 보인다. 실제 파일과 같이 '이미 있으면 즉시 return' 하는 IIFE 라,
안쪽 함수들은 pre-parse 만 되는 것까지 같은 조건이다.)

스캔 한 번(0.021 ms)의 **두 배**고, 최악값은 스캔 최악(0.044 ms)의 **네 배**다. 그러면서
두 번째 전송부터는 **하는 일이 아무것도 없다.**

**그래서 먼저 그냥 불러 본다.**

```js
// 1) 이미 준비돼 있으면 그대로 부른다. 흔한 경로는 여기서 끝난다.
const [ready] = await chrome.scripting.executeScript({
  target: { tabId },
  func: (p) => (window.__LM_READY__ ? window.__LM_MANGO__.run(p) : null),
  args: [payload],
});
if (ready && ready.result) return ready.result;
// 2) 이 문서에는 아직 없다. 그때만 넣는다.
```

| | 예전 | 지금 |
|---|---|---|
| 주입 왕복 — 문서당 첫 전송 | 2번 | 3번 (탐침이 하나 는다) |
| 주입 왕복 — 그다음 전송들 | 2번 | **1번** |
| 망고가 받아서 파싱하는 바이트 — 그다음 전송들 | 22,209 B | **0 B** |

첫 전송에서 왕복이 하나 느는 것은 받아들였다. 흔한 쪽은 압도적으로 '두 번째부터'이고
(목록을 한 번 띄워 놓고 주문건을 여러 개 옮긴다), 늘어나는 것은 **확장 쪽 IPC 한 번**인 반면
줄어드는 것은 **망고 페이지가 하는 일**이라 방향이 맞다.

**낡은 코드를 물고 있을 길이 없다.** 목록을 새로 검색하거나 저장이 끝나면 망고가 페이지를
통째로 다시 읽는다(폼 POST). 새 문서에는 `__LM_READY__` 가 없으니 그때는 알아서 다시 넣는다.

**`__LM_MANGO__` 가 아니라 `__LM_READY__` 를 보는 이유.** 두 파일은 나란히 넣는데(서로
기다릴 이유가 없다), 한쪽만 들어간 상태를 '준비됨'으로 볼 수는 없다 — `mango.js` 만 들어가고
`mango_main.js` 가 빠지면 저장할 때 `confirm` 자동 승인이 돌지 않는다. `__LM_READY__` 는
**두 주입이 모두 끝난 뒤의 run 호출에서** 세우므로, 서 있으면 둘 다 들어갔다는 뜻이다.
왕복은 늘지 않는다 (어차피 부를 호출에 한 줄 얹었다).

#### 표와 헤더도 문서당 한 번만 찾는다 (2026-08-31 실측)

스캔이 매번 내던 문서 조회 셋(`querySelector` + `closest` + 헤더 읽기)은 **전송마다 같은
답**을 낸다. [선택수정] 버튼을 문서당 한 번만 찾는 것과 같은 사정이라, 같은 장치를 붙였다.

| | 지금 | 캐시 |
|---|---|---|
| 표·칸 위치 찾기 | 0.0035 ms (최악 0.0049) | **0.0001 ms** (최악 0.0001) |

스캔 전체로는 이렇다. 두 구현을 **같은 시행 안에서 번갈아** 재서 기계 상태 차이를 없앴다
(500회 × 21시행 중앙값 / 최악).

| 행 스캔 | 예전 | 지금 | |
|---|---|---|---|
| 0건 일치 (가장 흔함) | 0.0208 ms (최악 0.0340) | **0.0158 ms** (최악 0.0258) | −24% |
| 1건 일치 | 0.0234 ms (최악 0.0316) | **0.0192 ms** (최악 0.0218) | −18% / 최악 −31% |

여기서도 중앙값보다 **최악값이 더 많이 줄었다.**

**낡았는지 스스로 확인한다.** 표가 갈려 나갔으면 `isConnected` 가 false 라 다시 찾고,
표는 그대로인데 헤더 행이 새로 그려졌으면 그 행이 **다른 객체**라 칸 위치를 다시 읽는다.
(`table.rows` 라이브 컬렉션을 캐시하는 것과는 다르다 — 그건 행이 바뀌면 값이 어긋나지만,
이건 '표가 무엇인가'와 '칸이 몇 번째인가'라서 문서 안에서 변할 일이 없다.)

바꾸기 전후로 **후보 목록과 점수가 완전히 같은 것을 54가지 경우에서 확인했다** — 목록
50행의 수령인 전부, 빈 이름, 없는 이름, 발주처 태그 1개, 태그 배열 2개. 표를 일부러 낡게
만들었을 때 다시 찾아오는 것도 확인했다.

#### 1단계 필터 루프는 이미 바닥이다 (2026-08-31 재확인)

스캔에서 남은 것은 사실상 51행을 도는 1단계 필터 하나다 (0.0178 ms — 스캔의 90%).
네 가지 대안을 같은 목록에서 재 봤고, **전부 더 느렸다.**

| 51행에서 수령인 칸 읽고 거르기 | 중앙값 | 최악 |
|---|---|---|
| **`tr.cells[rc].textContent` (지금)** | **0.0178 ms** | **0.0204 ms** |
| `firstElementChild` + `nextElementSibling` 걷기 | 0.0185 ms | 0.0286 ms |
| `firstChild.data` (텍스트 노드 직접, 가드 포함) | 0.0191 ms | 0.0215 ms |

#### 이제 어느 단계도 레이아웃을 읽지 않는다

위 표의 숫자보다 중요한 성질이다. `offsetParent`·`getBoundingClientRect`·`innerText` 는
**강제 리플로우**라, 요소 1.7만 개짜리 이 페이지에서는 브라우저가 마침 레이아웃을 다시 계산해야
하는 상태일 때 비용이 몇 배로 튄다. 평균값만 보면 안 보이고, 사용자가 뭔가 하던 중에 눌렀을 때만
느껴지는 종류의 비용이다.

마지막까지 남아 있던 곳이 간단메모 칸 고르기였다 (보이는 칸만 남기려 `offsetParent`, 화면 순서로
정렬하려 `getBoundingClientRect().y`). 셀 안에서는 **DOM 순서가 곧 화면 순서**라(50행 전부 확인)
숨은 저장칸만 걸러내면 같은 결과가 나온다.

| 간단메모 칸 고르기 | 레이아웃 깨끗할 때 | 레이아웃 더러울 때 |
|---|---|---|
| `offsetParent` + `getBoundingClientRect` | 0.014 ms | **0.065 ms** |
| DOM 순서만 | 0.002 ms | **0 ms** |

전체 경로(스캔 + 메모 + 선택수정 버튼 + 체크 해제)를 레이아웃을 일부러 더럽혀 가며 돌려도
깨끗할 때와 차이가 없다. 리플로우가 남아 있으면 여기서 몇 배로 벌어진다 — 망고 화면 구조를
건드릴 때 이 측정을 다시 해 보면 된다.

| 전체 경로 | 레이아웃 깨끗할 때 | 레이아웃 더러울 때 |
|---|---|---|
| 예전 측정 | 0.10 ms | 0.07 ms |
| 2026-08-31 (표에서 행 얻기 + 버튼 캐시) | 0.0485 ms | **0.0465 ms** |
| 2026-08-31 (헤더 끊기 + 버튼 선택자 좁히기 + 1단계 펴기) | **0.0447 ms** | — |

`table.rows`·`cells`·`querySelector`·`isConnected` 는 모두 레이아웃을 읽지 않는다. 이번에
추가된 것 중 리플로우를 부르는 건 없다.

> 마지막 줄은 **레이아웃**이 아니라 **DOM 변경**에 흔들리는지를 따로 쟀다 (0.0447 → 0.0460ms).
> 아래 'CJ온스타일' 절의 '페이지 상태에 흔들리지 않는다' 참고 — 라이브 컬렉션 캐시가 식는 쪽은
> 리플로우와 다른 축이라 표를 섞지 않았다.

`showPicker()` 의 `scrollIntoView` 는 예외로 남겨 뒀다. 후보가 2건 이상일 때만 도는 데다,
그건 성능이 아니라 사용자에게 후보를 보여주려는 동작 자체다.

#### NBSP 자리표시가 이 그림을 바꾸지 않는다 (2026-08-31 실측)

간단메모 앞칸을 NBSP 로 채우는 코드(`MEMO_PAD`)가 추가됐다. 값 쓰기가 한 번 늘어나므로
30행 목록에서 다시 쟀다.

| | 시간 |
|---|---|
| 측정 기준선 (빈 함수) | 0.00026 ms |
| NBSP 자리표시 단계 | 0.00235 ms |
| **순수 추가 비용** | **0.0021 ms** |
| 전송 1건의 전체 경로 (스캔 + 메모 + 체크 해제 + 버튼 찾기) | 0.054 ms |

전체의 4% 이고 절대값은 **2 마이크로초**다. 전송 한 건에 **한 번** 호출된다.

**리플로우도 늘지 않는다.** 레이아웃을 읽지 않고 쓰기만 했을 때의 비용(0.0022 ms)이 위 값과
같다 — 강제 리플로우가 걸렸다면 여기서 벌어진다. `.value` 는 쓰기도 읽기도 레이아웃과 무관하고,
`writeMemo()` 는 원래부터 이 칸에 값을 쓰고 있었으므로 레이아웃 무효화 횟수 자체가 그대로다.

> 참고로 값을 쓴 **뒤에 레이아웃을 읽으면** 0.74~0.91 ms 가 든다. 이건 NBSP 와 무관하게
> (패딩 없는 예전 코드도 같다) 이 페이지의 성질이고, 우리 코드는 쓰고 나서 레이아웃을 읽지
> 않으므로 실제로는 발생하지 않는다. 나중에 이 경로에 `offsetHeight` 류를 하나라도 넣으면
> 그 순간 0.9 ms 가 생긴다는 뜻이다.

함수 안을 더 줄여 보려고 세 가지를 만들어 재 봤지만(패딩 루프와 잇는 루프를 합치기, 슬롯 배열
할당까지 없애기) 0.0136~0.0144 ms 로 서로 구분되지 않았다. 결과도 네 가지 입력에서 모두 같다.
측정으로 구분되지 않는 차이 때문에 읽기 어려운 코드로 바꾸지는 않았다.

#### 1단계 필터만 손으로 편다 (2026-08-31 실측)

행마다 도는 구간은 후보 판정의 **1단계 하나뿐**이다. 여기서만 `cellText()` 호출을 펴고

`cellText()` 자체는 그대로 뒀다 — `score()` 가 결제금액·주문번호 칸을 읽는 데 쓰는데,
그쪽은 1단계를 통과한 소수의 행에서만 돈다. 폴백 규칙(칸을 못 찾으면 행 전체 텍스트)도
글자 그대로 같게 뒀고, 목록의 수령인 50명 + 부분일치 케이스 전부로 예전 코드와 대조해

### 값을 쓸 때 이벤트를 쏘지 않는다

한 번 보낼 때 확장이 망고 페이지에서 하던 일의 **절반이 이벤트 dispatch 15발**이었다
(입력칸 4개 × `input`·`change`·`keyup`, 그리고 체크 해제마다 `change`).

망고 화면을 열어 핸들러를 직접 확인한 결과, 우리가 건드리는 칸에 붙어 있는 건 jQuery 로
걸린 것 하나씩뿐이었다.

| 칸 | 걸린 이벤트 | 하는 일 |
|---|---|---|
| `uid_usd_order_num` · `uid_usd_order_price` · `uid_usd_delivery_num` | `keyup` | **그 행의 체크박스를 켠다** |
| `uid_state` (주문상태) | `change` | 같음 |
| `uid_check[]` (체크박스) | — | 핸들러 없음 |
| 간단메모 칸 (`.msp-*`) | — | 핸들러 없음 (**단, 아래 단서**) |

`input` 은 어디에도 걸려 있지 않고, 핸들러의 효과(행 체크)는 **`apply()` 가 곧바로 덮는다** —
어차피 전체 체크를 풀고 대상 행만 다시 켜기 때문이다. 저장을 맡는
`really_all_select_modify()` 도 체크된 행의 값을 id 로 `.val()` 해서 읽어 JSON 으로 싣고
`submit()` 할 뿐, '수정됨' 표시 같은 건 보지 않는다.

그래서 이벤트를 전부 뺐다. dispatch 15발과, 그중 `keyup`/`change` 핸들러가 부르는
**문서 전체 jQuery 조회 4번**이 같이 사라진다. (`click` 은 원래도 쓰지 않는다 — 체크 상태가
다시 뒤집힌다.)

> 망고 화면이 바뀌면 이 전제도 바뀔 수 있다. 확인 방법은
> `jQuery._data(document.getElementById('uid_usd_order_num_<uid>'), 'events')`.

#### 간단메모만은 예외다 — 숨은 칸을 직접 다시 만든다

간단메모 칸에는 **저장되는 값과 화면에 보이는 칸이 따로 있다.** 다른 네 칸은 우리가 쓰는
요소가 곧 저장되는 요소지만(`uid_usd_order_num_<uid>` 등 id 로 `.val()` 해 간다), 메모는
저장되는 값이 숨어 있는 `uid_usd_memo_<uid>`(`name="uid_usd_memo[]"`) **하나**뿐이고,
보이는 입력칸 3개는 그 값을 줄 단위로 쪼개 놓은 편집 UI 다.

사람이 타이핑하면 사이트 핸들러가 세 칸을 도로 합쳐 숨은 칸에 넣는데, 이벤트를 빼면서
그 합치기가 돌지 않게 됐다. 증상이 조용하다 — **화면에는 URL 이 보이고 성공 토스트도 뜨는데
저장하고 나면 메모만 비어 있다.** 다른 값(주문번호·금액·결제일시·주문상태)은 멀쩡히 들어간다.

그래서 `writeMemo()` 가 보이는 칸에 쓴 뒤 위 규칙으로 숨은 칸을 직접 다시 만든다. 이벤트는
여전히 하나도 쏘지 않는다. (규칙은 망고 목록 50행 전부에서 확인했다.)

```
uid_usd_memo_<uid>  =  비어 있지 않은 보이는 칸들을 '
' 로 이은 것
```

##### 앞칸이 비면 URL 이 밀린다 — NBSP 로 자리를 지킨다

URL 은 2번 칸에 넣는데(맨 위 표), **1번 칸이 비어 있으면 그대로는 1번 칸으로 밀려 올라간다.**
숨은 칸이 `URL` 한 줄이 되고, 저장 후 다시 그려질 때 첫 줄이 곧 1번 칸이기 때문이다.

빈 줄로 자리를 지워 보려 했지만 안 된다. **서버가 각 줄을 trim 하고 빈 줄을 버린다** —
2026-08-31 에 실제로 저장해 보고 재조회해서 확인했다.

| 저장한 값 | 재조회하면 | URL 위치 |
|---|---|---|
| `"\nURL"` (빈 줄) | `"URL"` | 1번 칸 ✗ |
| `" \nURL"` (공백 한 칸) | `"URL"` | 1번 칸 ✗ |
| `"\u00a0\nURL"` (NBSP) | `"\u00a0\nURL"` | **2번 칸 ✓** |

그래서 앞칸을 `MEMO_PAD` = NBSP(U+00A0) 로 채운다. 서버 trim 을 통과해 그대로 살아남고
(U+3000·U+200B 도 통과하는 것을 같이 확인했다), 화면에서는 그냥 빈 칸으로 보인다.
앞칸을 채우고 나면 잇는 규칙은 위의 사이트 원래 규칙 그대로여도 결과가 같다.

> 서버가 `trim()` 문자셋을 바꾸면(NBSP 를 자르기 시작하면) 이 방법이 깨진다. 증상은 예전과
> 같다 — URL 이 1번 칸에 붙는다. 확인은 한 건 저장 후 재조회해서 1번 칸 코드포인트를 보면 된다.

칸을 고를 때 레이아웃을 읽지 않는다 — 셀 안의 네 요소는 항상 `보이는 칸 3개 + 숨은 저장칸`
순서이고 DOM 순서가 곧 화면 순서다. 숨은 저장칸은 `uid_usd_memo_<uid>` 자기 자신으로 걸러낸다.
(위 '레이아웃을 읽지 않는다' 참고.)

실측해 두면 좋을 두 가지 (2026-08-31, 코드는 이미 둘 다 견디게 되어 있다):

- **네 요소의 태그가 섞여 있다** — `input[type=text]`, `textarea`, `input[type=text]`, 그리고
  숨은 저장칸도 `textarea` 다. `input[name="uid_usd_memo[]"]` 로 찾으면 **하나도 안 잡힌다.**
  `writeMemo()` 는 id 로 숨은 칸을 잡고 `input[type=text], textarea` 로 슬롯을 모으므로 무관하다.
- **페이지가 `Array.prototype.find` 를 덮어써 두었다** — 네이티브가 아니고 요소가 아니라
  **인덱스(Number)** 를 돌려준다. 콘솔에서 `boxes.find(b => b.value === uid).checked = true` 가
  조용히 아무 일도 안 하는 이유다. 확장 코드는 isolated world 에서 돌아 영향을 받지 않지만,
  **페이지 콘솔에서 디버깅할 때는** 인덱스 루프를 쓸 것.

### 그 밖의 절약

- **[선택수정] 버튼을 `onclick` 속성으로 한 번에 집고, 문서당 한 번만 찾는다.** 예전에는
  `a`·`button`·`input[type=button]` **1,543개**를 돌며 `innerText` 를 읽어 라벨이 `선택수정` 인
  것을 찾았다. 요소마다 레이아웃을 강제하는 데다 0.49ms 다.
  `[onclick*="really_all_select_modify"]` 는 0.016ms 이고, 찾은 요소를 들고 있다가 `isConnected`
  로만 확인하므로 두 번째 전송부터는 0이다. 망고가 핸들러 이름을 바꾸면 예전 방식(단
  `textContent`)으로 떨어진다.
- 행 스캔에 `innerText` 대신 `textContent` 를 쓴다 (`innerText` 는 행마다 레이아웃을 강제한다).
- **행 목록을 문서가 아니라 `table.rows` 에서 얻는다.** 체크박스는 수령인 칸 관문을 통과한
  행에서만 집는다 — 문서 조회가 50개 수집 + `closest` 50번에서 **첫 체크박스 하나**로 줄었다.
- 경로 어디에서도 레이아웃을 읽지 않는다 (`offsetParent`·`getBoundingClientRect`·`innerText`
  가 전부 빠졌다 — 위 '이제 어느 단계도 레이아웃을 읽지 않는다' 참고).
- 후보 선택 UI 를 띄운 적이 **없으면** `clearPicker()` 는 문서를 훑지 않는다. `run()` 이
  시작할 때마다 무조건 부르는 자리라, 압도적으로 흔한 '한 방에 매칭' 경로에서 문서 조회
  3번이 통째로 사라진다.
- 체크 해제도 문서를 다시 훑지 않고 후보를 고를 때 찾아 둔 표의 행만 돈다 (0.013ms — 문서
  조회로 다시 모으면 0.026ms 다). 선택수정이 읽는 값은 `uid_check[]` 뿐이라 그 표의
  체크박스가 곧 전부다. **매칭에 실패한 전송에서는 아예 돌지 않는다.**
- 망고 탭이 여러 개면 **사용자가 보고 있던 탭부터** 시도한다. 거기서 끝나면 나머지 탭에는
  스크립트를 주입조차 하지 않는다.
- 자동 저장 경로에서는 하이라이트·스크롤을 하지 않는다 (어차피 곧바로 페이지가 갱신된다).
- **주입 왕복 3번 → 2번.** `mango_main.js`(MAIN) 와 `mango.js`(ISOLATED) 는 서로를 기다릴
  이유가 없어 나란히 넣는다. 앞엣것은 `window` 리스너를 하나 걸어둘 뿐이고 그 리스너는
  저장 직전에야 불린다.
- 탭을 앞으로 가져올 때 `chrome.tabs.get` 을 다시 부르지 않는다. `chrome.tabs.query` 가
  `windowId` 를 이미 실어 준다.
- 발주처 태그 배열은 스캔 전에 **한 번** 만든다. 판정도 `some(화살표함수)` 대신 손으로 도는
  루프다 — 행마다 클로저를 만들지 않기 위해서다.
- 표(`<table>`)는 후보를 고를 때 찾아 둔 것을 저장 단계까지 들고 간다 (`closest` 재탐색 없음).

### 없앤 것 — 수령인 검색 이동

예전에는 열려 있는 탭에서 못 찾으면 수령인 이름으로 검색한 URL 로 망고 탭을 이동시켰다.
이게 확장에서 압도적으로 비싼 단계였다. 위의 스캔들이 0.05ms 단위인데, 목록 재로딩은
**초 단위**다 (요소 1.8만 개 + 서버 왕복). 게다가 사용자가 보던 목록·스크롤·체크 상태가 날아간다.

대상 주문건을 띄워 놓고 버튼을 누르는 흐름이라 그 왕복은 통째로 낭비여서 걷어냈다.
목록에 주문건이 없으면 아무것도 건드리지 않고 멈춘다. `searchUrl`·`waitForLoad`·`ymd`
함수도 같이 사라졌다.

### 마켓 페이지 쪽

- SSG는 버튼 자리를 찾을 때 **텍스트 노드를 훑는 빠른 경로**를 먼저 쓴다. 요소마다
  `textContent` 를 만드는 방식은 조상이 자손 텍스트를 다시 이어붙여 문서가 커질수록 비용이
  급격히 는다. 주문번호가 여러 요소로 쪼개진 경우에만 전수 조사로 넘어간다.
- 버튼 자리를 기다리는 `MutationObserver` 는 **150ms 에 한 번**으로 묶는다. 로딩 중
  DOM 변경마다 문서를 훑지 않기 위한 것이고, 보통 첫 시도에 이미 붙는다.

#### 롯데아이몰 — 문서 전체를 훑는 질의를 만들지 않는다 (2026-08-31 실측)

바뀌어도 캐시가 날아가** `querySelectorAll` 과 같아진다. 이 페이지에는 초 단위로 도는 방송

| B. 라이브 컬렉션으로 전부 교체 | **0.013 ms** | 0.121 ms |

걷어낸 것과 같은 이유로 피했다 — 평균이 아니라 **최악이 안 튀는 쪽**을 고른다. C 는 캐시 상태와
무관하게 0.025ms 이고, A 대비 warm 2.3배·cold 2.8배 싸다.

| 확장이 넣은 스타일시트 (`chrome-extension://`) | **0개** |

`content_scripts` 매칭 패턴이 **열세 개**가 됐지만 망고(`tmg4087.mycafe24.com`)에 걸리는 건
여전히 **0개**다. 넓힌 것은 `www.hmall.com/mo/*` 지 망고가 아니고, `watch` 옵저버도 그
도메인 안에서만 산다. 망고는 `host_permissions` 에만 있어 전송 버튼을 눌렀을 때만 코드가 닿는다.

**전송할 때 쓰는 시간도 GS SHOP·NS몰 절의 표와 같다.** 현대몰 payload(`total` 있음, 발주처
태그 없음)로 같은 목록에서 쟀다 (500·300회 × 15시행 중앙값 / 최악).

| 행 스캔 | 중앙값 | 최악 |
|---|---|---|
| 0건 일치 (가장 흔함) | 0.016 ms | 0.023 ms |
| 1건 일치 | 0.018 ms | 0.024 ms |
| 51행 전부 1단계 통과 (최악) | 0.128 ms | 0.167 ms |
| 〃 + 발주처 태그 1개 | 0.285 ms | 0.403 ms |
| 〃 + 발주처 태그 3개(배열) | 0.314 ms | 0.467 ms |

태그를 하나라도 지어내 실으면 최악이 **두 배**가 된다는 것도 그대로다 — 현대몰이 태그를
비워 둔 이유다. 어댑터가 하는 일은 전부 `www.hmall.com` 안에서 끝나고, 미리 받아 둘 API 도
없어(값이 전부 DOM 에 있다) 클릭이 기다리는 왕복이 하나도 없다. 망고에 들어오는 건 값
여섯 개짜리 payload 하나뿐이다.

### confirm 자동 승인 방식

망고의 `really_all_select_modify()` 는 `confirm('수정하시겠습니까?')` 를 거친다.
콘텐츠 스크립트는 격리된 컨텍스트라 페이지의 `window.confirm` 을 바꿀 수 없으므로,
`mango_main.js` 를 `world: "MAIN"` 으로 **필요할 때 주입해** 페이지 컨텍스트에서 실행시킨다.
저장 직전 `LM_SUPPRESS_CONFIRM` 커스텀 이벤트를 쏘면 그 스크립트가 `window.confirm` 을
`() => true` 로 잠깐 바꾸고, 3초 뒤 원래대로 되돌린다. `alert` 은 건드리지 않으므로
망고가 내는 검증 오류 메시지는 그대로 보인다.

## 브라우저 사이 다리 (`relay/`)

의존성 없는 Node 서버 하나가 `127.0.0.1:8787` 에서 값을 잠깐 들고 있는다. 루프백에만 묶어서
같은 기기의 브라우저끼리만 닿는다.

| | 조건 | 하는 일 |
|---|---|---|
| 보내는 쪽 | 이 브라우저에 망고 탭이 **없다** | `POST /send` 로 넘기고 끝 |
| 받는 쪽 | 이 브라우저에 망고 탭이 **있다** | `GET /pending` → 반영 → `POST /ack` |

**역할을 설정하지 않는다.** 망고 탭이 열려 있는 브라우저가 곧 받는 쪽이다. 세 브라우저에
똑같은 폴더를 로드하면 각자 알아서 자기 역할을 한다.

### 왜 '창 포커스'가 신호인가

MV3 service worker 는 30초면 잠든다. 받는 쪽을 계속 깨워 두려면 WebSocket 을 물고 있거나
주기적으로 두드려야 하는데, 어차피 **결과를 보려면 크롬 창을 띄워야 한다.** 그래서
`chrome.windows.onFocusChanged` 를 신호로 쓴다.

- 상주 비용이 0이다. 크롬을 안 쓰는 동안 확장은 한 줄도 돌지 않는다.
- 사용자가 크롬으로 넘어오는 그 순간에 이미 반영돼 있다.
- 포커스 이벤트를 놓쳤거나 실패해서 남은 건은 **확장 아이콘을 눌러** 직접 밀어 넣는다.

망고 페이지에 상주 코드를 두지 않는다는 원칙도 그대로다 — 받는 쪽도 **반영할 게 실제로
있을 때만** 주입한다. 큐가 비어 있으면 `GET /pending` 에서 끝나고 망고 페이지는 건드리지도
않는다.

### 망고를 반복해서 긁지 않는다 — 실패는 자동 재시도하지 않는다

릴레이를 붙이면서 **확장이 망고를 느리게 만들 수 있는 경로가 딱 하나 생겼다.**

신호가 '창 포커스'인데, 반영 실패의 압도적 다수는 *그 주문건이 지금 목록에 없다* 이고
그건 사용자가 목록을 바꾸기 전까지 계속 실패한다. 막아두지 않으면 **창을 오갈 때마다**
망고 페이지에 스크립트를 주입하고 목록 전체를 훑게 된다. 알트탭 한 번에 한 번씩이다.

그래서 실패한 건의 id 를 적어 두고 `GET /pending?skip=…` 으로 넘긴다.

- 막힌 건은 **확장 아이콘을 눌렀을 때만** 다시 시도한다 (`drain(force)` 가 목록을 비운다).
- 뒤의 건들은 그대로 흘러간다. 한 건이 막혀도 큐 전체가 멈추지 않고, 큐 순서도 그대로다.
- 목록은 `chrome.storage.session` 에 둔다. service worker 가 30초마다 잠들어도 유지되고,
  브라우저를 닫으면 같이 사라진다 (다음에 켤 땐 상황이 바뀌었을 테니 한 번은 다시 해볼 만하다).

포커스 이벤트 자체도 **1.5초 안에 겹쳐 오면 무시한다.** 창을 몇 번 오갈 때마다 탭을 훑고
릴레이를 두드릴 이유가 없다. 그리고 `drain()` 은 **망고 탭이 있는지부터 확인하고 끝낸다** —
웨일·엣지는 이 한 줄 때문에 포커스가 바뀌어도 릴레이를 두드리지조차 않는다.

### 꺼낸다고 지우지 않는다

`GET /pending` 은 **맨 앞 것을 보여주기만** 하고, 받는 쪽이 실제로 반영에 성공해
`POST /ack` 를 보내야 큐에서 빠진다. 망고 목록에 그 주문건이 아직 없어서 실패하는 일이
흔한데, 그때 값을 잃으면 안 되기 때문이다. 목록을 맞춰 놓고 확장 아이콘을 다시 누르면 된다.

- 후보 동점이라 **사람이 골라야 하는 상태**(`needsPick`)도 ack 한다. 선택 UI 가 이미 망고
  화면에 떠 있는데 지우지 않으면, 창을 옮길 때마다 같은 UI 가 다시 뜬다.
- **한 번에 한 건만** 처리한다. 반영에 성공하면 망고가 `[선택수정]` 으로 페이지를 다시 읽어
  목록이 통째로 바뀐다. 이어서 두 번째를 밀어 넣으면 바뀐 목록 위에서 매칭하게 된다.
- 6시간이 지난 건은 버린다. 브라우저를 며칠 안 켠 뒤 뒤늦게 반영되면 곤란하다.
- 넘어온 값은 `url`·`orderNo`·`price`·`payDate`·`receiver` 가 다 있는지 확인하고 받는다.
  루프백이라도 아무거나 큐에 쌓이면 결국 망고에 그대로 써진다.

## 참고 — 확인된 제약

### 공통

- **롯데온·SSG·패션플러스·롯데아이몰·CJ온스타일은 결제 시각이 없고 날짜만** 얻을 수 있다 (`2026.08.27`). 무신사는 영수증에서
  `2026-08-28 10:03:46`, 네이버페이는 주문상세 화면에서 `2026.08.26 08:24:52`, 지마켓은 주문상세 API 에서
  `2026.08.31 08:19:56` 으로 시각까지 들어간다.

### 롯데온

- 주문상세에 결제 시각이 없다. 시간까지 필요하면 롯데온 내부 API 호출이 필요한데,
  Imperva 봇탐지에 걸릴 위험이 있어 채택하지 않았다.
- 결제수단이 여러 개(예: 네이버페이 + L.POINT)면 **`원` 단위 금액만 합산**하고 `P`(L.POINT)는 제외한다.

### SSG

- **전자영수증의 `발급일시` 는 결제일시가 아니다.** 영수증을 뽑은 시각이라 누를 때마다 지금 시각이
  찍힌다 (주문 2026-08-27, 발급일시 2026-08-30 15:51:23). 영수증 결제내역의 `승인일시` 도
  `2026/08/27` 로 날짜뿐이다. 그래서 영수증을 아예 열지 않고, 주문상세 상단의 주문일자를 쓴다.
  - 영수증 팝업 주소는 `pay.ssg.com/myssg/showReceiptPopup.ssg?orordNo=<주문번호>` 로 규칙적이라
    필요해지면 fetch 로 바로 읽을 수 있다.
- 주문번호 표기가 세 군데 다 다르다 — 화면 `20260827-61F020`, URL `2026082761F020`,
  영수증 `2026-08-27-61F020`. 망고에는 **화면 표기**를 넣고, 버튼 위치를 찾을 때는
  하이픈을 떼고 URL 값과 대조한다.
- 주문일자는 주문번호 앞 8자리(`YYYYMMDD`)와 같다. 화면에서 날짜를 못 찾으면 여기서 유도한다.
- 수령인 라벨이 `받는 분` 이 아니라 **`받으시는 분`** 이고, 값에 전화번호와 괄호주석이
  붙는다 (`양은영 010-2977-8032 (안심번호 사용안함)`). 숫자·괄호가 나오는 지점에서 자른다.
- 구입금액은 `총 결제금액`(30,253원)을 쓴다. SSG MONEY 로 결제한 몫(635원)은 이미 빠져 있어
  롯데온에서 L.POINT 를 제외하는 규칙과 결이 같다. 상품 자체 가격(30,888원)이 아니다.

### 무신사

- **영수증 화면이 PG사마다 다르다.**
  - 페이코 결제 → `pay.musinsapayments.com/mps/receipt/...` 가 HTML 로 다 내려준다.
    라벨이 `승인`, 값이 `2026-08-28 10:03:46`.
  - 무신사페이 결제 → 위 주소에서 `dashboard.tosspayments.com/receipt/sales-slip?...` 로
    넘어가고, 값을 **자바스크립트로 그린다**(HTML 만 받으면 날짜가 없다). 라벨도 `승인` 이 아니라
    `결제일시` 다.

  그래서 영수증은 fetch 로 파싱하지 않고 **background 가 백그라운드 탭으로 실제로 띄워
  읽고 닫는다**. 두 화면 모두 같은 정규식 하나로 잡힌다 (`승인일시|결제일시|승인` 뒤의
  `YYYY-MM-DD HH:MM(:SS)`). `승인번호` 뒤에는 숫자가 바로 붙어서 날짜 패턴에 걸리지 않는다.
  - content script 는 CORS 때문에 애초에 이 주소를 `fetch` 할 수 없다 (`Failed to fetch`).
  - 페이코 영수증 HTML 에는 **주석 처리된 예시 날짜**(`2023.04.08 22:42:17`)가 들어 있다.
    `innerText` 로 읽으므로 주석은 보이지 않지만, HTML 을 직접 정규식으로 훑는다면 이걸 조심할 것.
- 영수증을 못 읽으면 **거래명세서**(`/order-service/my/order/payment_receipt/<주문번호>`)의
  `주문 일자` 로 떨어진다. 같은 오리진 + 서버렌더라 그냥 `fetch` 로 읽힌다. 다만 **분 단위**이고
  점으로 찍혀 있어(`2026.08.27 08:32`) 영수증 표기에 맞춰 `-` 로 바꾼다. 그것도 실패하면
  주문 API 의 `orderDatetime`.
- 화면 값은 `/order-service/my/order/get_order_view/<주문번호>` JSON 에서 온다. 수령인은
  `orderInfo.r_nm`. 화면에는 수령인 라벨이 없어서(이름·주소·전화번호가 그냥 나열된다)
  DOM 으로는 안정적으로 못 뽑는다 — 이 값은 API 가 유일한 출처다.
- **즉시 할인가**는 카드사 즉시할인이 빠진 실제 청구액이다 (결제 금액 74,870 → 즉시 할인가 71,870).
  화면의 `결제 정보` 블록에서 라벨로 읽고, 블록을 못 찾으면 API 로 같은 규칙을 재현한다 —
  `promotion_discount_amt > 0` 이면 `without_recv_amt_promotion_discount_amt`, 아니면 `recv_amt`.
  두 경로가 같은 값을 내는 것을 확인했다.
  - `결제 금액` 줄에는 할인율 배지(`63%`)가 끼어 있다. 라벨 뒤 **`원` 이 붙은 첫 숫자**를 집는다.
- **SPA 다.** 주문목록에서 주문상세로 문서를 다시 읽지 않고 넘어간다. 그래서 무신사·네이버페이는
  `mount({ watch: true })` 로 붙는다 (아래 참고).
- 클래스 이름이 스타일드컴포넌트 해시(`PaymentInfo__PriceWrap-sc-7uk9xp-3`)라 빌드마다 바뀐다.
  선택자로 쓰지 않고 **한글 라벨 텍스트**로 찾는다.

### 네이버페이

- **`orders.pay.naver.com` 은 브라우저 자동화 도구로 열 수 없다** (SSG 와 같은 사정).
  그래서 화면 구조는 스크린샷으로 확인했고, 추출 로직은 그 화면 텍스트를 그대로 재현한
  가짜 DOM 에 `naver.js` 를 태워 검증했다. 값을 못 찾으면 오류 토스트에 결제정보 블록과
  배송지 주변 텍스트를 같이 실어 보낸다(`probe`) — 화면을 직접 볼 수 없을 때 원인을 좁히기 위한 것.
- **구입금액은 카드로 결제한 금액만** 쓴다. 네이버페이는 포인트를 섞어 결제하는 게 기본이라
  주문금액과 카드 청구액이 다르다 (주문금액 41,800 = 포인트 1,087 + 카드 간편결제 40,713 → **40,713**).
  롯데온에서 L.POINT 를, SSG 에서 SSG MONEY 를 빼는 규칙과 결이 같다.
  - 결제수단 줄을 고를 때 `카드` 가 들어가도 금액 줄이 아닌 것들을 걸러낸다 —
    마스킹된 카드번호(`현대 5165 **** **** ****`), 안내 문구(`무이자 … 카드사로 문의하시면`),
    할인 줄. 카드 두 장으로 나눠 결제했으면 둘 다 더한다.
- **결제일시는 주문번호 바로 위**에 `2026.08.26. 08:24:52` 로 찍혀 있다. 날짜 끝의 점만 떼고
  `2026.08.26 08:24:52` 로 넣는다. 주문번호 요소에서 위로 올라가며 찾으므로, 페이지 다른 곳의
  날짜(구매확정 예정일 등)를 집지 않는다.
- 수령인은 배송지 첫 줄인데 **배송지 별칭이 괄호로 붙는다** (`함용녀(집)`). 괄호부터 잘라낸다.
- **SPA 다.** 무신사와 같은 이유로 `mount({ watch: true })` 로 붙고, `anchor()` 는 찾은 요소를 캐시한다.
- 클래스 이름을 선택자로 쓰지 않고 한글 라벨 텍스트로 찾는다 (무신사와 같은 이유).

### 패션플러스

- **값이 전부 `<th>라벨 / <td>값` 표에 들어 있다.** 롯데온·SSG 처럼 본문 텍스트를 정규식으로
  훑지 않고 표를 라벨로 읽는다. 라벨 문구가 겹쳐도(주문자 정보·배송지 정보에 **`주문자명`이 둘 다**
  있다) 어느 표인지로 갈리기 때문에, 표를 그 위 제목(`결제수단 정보` / `배송지 정보`)으로 먼저 고른다.
- **수령인 라벨이 `받는 분`이 아니라 `주문자명`이다.** 주문자 정보의 주문자명(구매자)이 아니라
  **배송지 정보의 주문자명**을 쓴다. 값 칸에 `배송지 변경` 링크가 이름 뒤에 붙어 있어서
  (`서미경 배송지 변경`) 읽기 전에 `a`·`button` 을 걷어낸다.
- **구입금액·결제일시는 `결제수단 정보` 표에서** 가져온다 — `결제금액 44,700원`,
  `결제승인일 2026-08-29`. 위쪽 `최종 결제금액` 블록의 총 결제 예상금액은 같은 값이지만
  결제수단이 아니라 주문 기준이라, 망고 행 매칭 보조키(`total`)로만 쓴다.
  - 결제수단이 나뉘어 있으면 `결제금액` 줄이 여러 개일 수 있어 전부 더한다.
  - `총 결제 예상금액(1건)44,700` 처럼 금액 앞에 **`(1건)` 이 붙어** 있다. 괄호를 건너뛰지 않으면
    건수의 `1` 을 금액으로 집는다.
- 결제승인일은 `2026-08-29` 로 하이픈 표기다. 롯데온·SSG 와 맞춰 `2026.08.29` 로 바꿔 넣는다.
- **발주처 태그(`marketTag`)를 넘기지 않는다.** 망고 목록의 발주처 표기는 그 주문건을 어디서
  사왔는지가 아니라 망고에 등록된 공급처다.
  - 2026-08-31 에 600건을 훑어 보니 `[FashionPlus.co.kr]` 표기가 **18건 존재하기는 한다**
    (그 전에 확인했을 때는 패션플러스에서 산 건이 `[LOTTEON.com]` 으로 찍혀 있어 표기 자체가
    없는 줄 알았다). 즉 태그는 있지만 **이번에 어디서 샀는지와 일치한다는 보장이 없다.**
  - 잘못 걸리면 엉뚱한 행의 점수를 올린다. 맞아도 +2 를 벌 뿐이라 넘기지 않는 쪽을 유지한다.
- 주문번호는 URL 경로에서 읽는다 (`/mypage/order/detail/141324230`). 화면 제목 줄에도
  같은 번호가 `141324230 (신청일: 2026-08-29)` 로 찍혀 있어 그 옆이 버튼 자리다.
- **Vue 가 우리 버튼을 죽은 껍데기로 다시 그린다.** SPA 는 아니지만 `mount({ watch: true })`
  로 붙는 이유다.
  - 주문상세 영역(`#my_order_detail`)에 **Vue 2.6.12 가 마운트**한다. `el` 만 주고 `render`
    함수가 없으면 Vue 2 는 **그 요소의 기존 DOM 을 템플릿으로 컴파일해 새로 그린 뒤 통째로
    교체**한다. `document_idle` 에 먼저 붙은 우리 버튼도 그 템플릿에 섞여 들어가,
    **마크업·CSS 는 똑같은데 클릭 리스너만 없는 복제본**으로 다시 태어난다.
  - 증상이 고약하다 — 버튼은 멀쩡히 보이는데 **눌러도 아무 일도 일어나지 않는다.** 토스트도,
    `전송 중…` 라벨 변화도 없다. 확장 오류가 아니라 리스너가 애초에 없는 것이라 콘솔도 조용하다.
  - 확인 방법: `getComputedStyle`·`elementFromPoint`·이벤트 전파는 전부 정상인데
    `버튼.click()` 조차 무반응이면 이 경우다. 마운트가 끝난 뒤 같은 자리에 손으로 붙인
    버튼은 정상 동작한다. `조상요소.__vue__` 로 어디에 마운트했는지 알 수 있다
    (단, `__vue__` 는 MAIN 월드 속성이라 content script 에서는 안 보인다).
  - 대응은 `watch: true` 다. 옵저버가 살아 있으니 Vue 가 다시 그린 직후 틱에 진짜 버튼을
    다시 붙인다. 남아 있는 껍데기는 `common.js` 의 `place()` 가 걷어낸다 — 붙이기 직전에
    `.lm-send-btn[data-lm-key="<자기 key>"]` 중 자기 자신이 아닌 것을 지운다.

### 지마켓

- **주문번호가 두 종류다.** URL 경로와 결제정보 헤더에 찍히는 건 `장바구니번호`(`5523612421`)이고,
  상품 옆에 `주문번호`로 찍히는 건 상품별 번호(`4484872454`)다. 망고에는 **상품별 주문번호**를 넣고,
  간단메모의 주문상세 URL 에는 장바구니번호가 들어간다 (URL 이 그렇게 생겼다).
- **상품마다 주문번호·결제금액·카드전표가 따로다.** 그래서 버튼도 상품마다 하나씩 붙이고, 누른
  자리의 상품만 보낸다 — `common.js` 의 `key` 가 이걸 위해 생겼다 (아래 '마켓 추가하기' 참고).
  - 다만 이 계정의 최근 주문 50건은 전부 상품 1개짜리였다. 복수 상품 화면은 주문번호 칸을 복제해
    흉내낸 상태로만 확인했다 (버튼 두 개가 서로를 걷어내지 않고 각자의 상품을 보내는 것까지).
- **값은 클릭하기 전에 미리 받아 둔다.** 버튼이 붙는 순간 API 를 한 번 부르고 그 화면을 보는
  동안 들고 있는다 — 클릭했을 때 기다리는 시간이 322ms → 0.3ms 가 된다 (위 '망고 페이지 성능'
  다음의 지마켓 실측 참고).
- **값은 화면이 아니라 같은 오리진 API 에서 읽는다** — `GET /api/pay-detail/<장바구니번호>`.
  주문상세 화면이 원래 부르는 그 요청이다. 화면에서 읽는 건 버튼 자리와 그 자리의 주문번호뿐이다.
  - 이유는 **결제일시가 화면에 아예 없기 때문**이다. 어차피 API 를 부를 거라면 금액·수령인도
    거기서 읽는 편이 어긋날 곳이 적다 (`payPayment` / `payDelivery` / `orderList`).
- **결제일시는 카드전표의 `거래일자`와 같은 값**을 API 에서 가져온다.
  - 전표는 `receipt.gmarket.co.kr/Card/CardReceipt?contr_no=<주문번호>` 로 주소가 규칙적이지만,
    HTML 로 값을 내주지 않는다 — `/Card/CardReceiptForm` 을 `seqNo`·`custNo`·`contrNo` 로 다시
    POST 해서 그린다. 그래서 읽으려면 무신사 영수증처럼 백그라운드 탭으로 띄워야 한다.
  - API 의 `payPayment.paymentDateTime` 이 같은 시각이라 탭을 열지 않는다. 실측 두 건 모두
    **전표가 1초 뒤**였다 (전표 `2026-08-31 8:19:57 AM` / API `08:19:56`, 전표 `8:00:24 AM` / API `08:00:23`).
    결제 요청과 카드 승인의 간격이다.
  - API 값은 UTC(`2026-08-30T23:19:56.373Z`)다. PC 시계가 어디에 맞춰져 있든 KST 가 나오도록
    UTC 에 9시간을 더해 UTC 게터로 읽는다.
- **구입금액은 카드 청구액**이다. 상품이 하나면 결제수단 목록에서 카드분만 더한다 (스마일캐시가
  섞이면 상품 결제금액보다 작다 — 롯데온의 L.POINT, SSG 의 SSG MONEY 를 빼는 규칙과 같다).
  상품이 여럿이면 카드분을 상품별로 나눌 근거가 없어 그 상품의 결제금액을 그대로 쓴다.
  - 확인한 주문은 전부 카드 단독 결제였다. 스마일캐시가 섞인 주문은 아직 못 봤다.
- **Next.js SPA 다.** 주문내역(`/ko/pc/list/all`) → 주문상세는 문서를 다시 읽지 않고 넘어간다
  (목록의 링크는 `/ko/pc/detail/<장바구니번호>`, 열리면 `/ko/pc/detail/basic/<장바구니번호>`).
  그래서 content script 를 `my.gmarket.co.kr/ko/pc/*` 전체에 붙이고 `watch: true` 로 따라다닌다.
  - 주문번호 칸(`button.button-copy`)은 **목록 화면에도 똑같이 있다.** 경로가 주문상세일 때만
    훑어서 목록에 버튼이 붙지 않게 한다.
- **발주처 태그(`marketTag`)가 없다** (패션플러스·롯데아이몰과 같은 사정 — 망고 발주처는
  등록된 공급처라 이번에 지마켓에서 샀다는 것과 별개다). 600건에도 지마켓 표기는 없었다.
  실제로 찍히는 표기가 확인되면 `extract()` 반환값에 한 줄만 추가하면 된다.

### 롯데아이몰

- 롯데온과 같은 롯데 계열이지만 **화면이 전혀 다르다** (`lotteimall.com` = 롯데홈쇼핑).
  롯데온 어댑터를 복사해 쓸 수 있는 부분이 없어 따로 만들었다. 서버가 HTML 을 다 그려서
  내려주므로 SPA 대응(`watch`)도, API 호출도 필요 없다.
- **값은 페이지 맨 아래 `결제/할인/적립` 오른쪽 블록(`.totalN`) 한 곳에 다 있다.**

  ```
  결제금액                                   88,540원      <- dl.total dd strong
  ┌──────────────┬──────────┬──────────────────────────────────────┐
  │ L.PAY 간편결제│ 88,540원 │ [2026.08.28] 하나카드(LOCAL) 승인     │  <- table.table_Ninfo
  │              │          │ [할부형태 : 일시불]                   │
  │              │          │ 카드청구 할인가 : 84,110원            │  <- p.paynoti_txt
  └──────────────┴──────────┴──────────────────────────────────────┘
  ```

- **구입금액은 `카드청구 할인가`가 있으면 그쪽을 쓴다** (88,540 → **84,110**). 카드사가
  청구서에서 깎아주는 몫이라 실제로 빠져나가는 돈은 승인금액이 아니다. 롯데온에서 L.POINT,
  SSG 에서 SSG MONEY 를 빼는 규칙과 결이 같다.
  - 총액에서 **할인분(승인액 − 청구액)** 을 빼는 식으로 계산한다. 결제수단이 하나면 결과가
    곧 `카드청구 할인가` 그 값이고, 여러 수단 중 카드분에만 청구할인이 붙어도 맞는다.
  - 페이지 자신이 `상기 금액은 실제 청구금액과 차이가 있을 수 있습니다` 라고 붙여 둔다.
  - 최근 주문 10건 중 청구할인이 붙은 건 하나카드 결제 2건이었다 (현대카드 3건에는 없었다).
- **결제일시 표기가 결제수단에 따라 다르다.** Npay 는 `2026.08.28 승인`, L.PAY 간편결제는
  `[2026.08.28] 하나카드(LOCAL) 승인`. 표 안에 날짜꼴 문자열이 이것뿐이라 대괄호를 신경 쓰지
  않고 첫 번째 `20xx.xx.xx` 를 집는다. 시각은 화면 어디에도 없다.
- **주문번호 표기가 두 가지다** — 화면 `2026-08-28-C20072`, URL `ord_no=20260828C20072`.
  망고에는 **화면 표기**를 넣고 (SSG 와 같은 결정), 간단메모의 URL 에는 URL 표기가 들어간다.
- 수령인은 배송지의 `받으시는 분` 인데 값이 `[배란영] 배란영 / 010-2977-8032` 꼴이다.
  앞 대괄호는 **배송지명**(주소록에 저장된 이름)이라 떼어내고, 전화번호 앞까지가 이름이다.
  - 같은 표의 `주문하시는 분`(계정 주인)과 헷갈리지 않도록 라벨로 행을 고른다.
- **발주처 태그(`marketTag`)를 넘기지 않는다.** 처음에는 `['롯데아이몰', '롯데홈쇼핑',
  'LOTTEIMALL']` 세 후보를 넣어 뒀는데, 망고 목록 600건(12페이지)을 실제로 훑어 보니
  발주처 슬롯에 찍히는 표기는 `[LOTTEON.com]`·`[SSG.com]`·`[MUSINSA.com]`·`[FashionPlus.co.kr]`
  넷뿐이었다. **전부 도메인 꼴**이라 세 후보 중 어느 것도 맞을 수가 없다. 게다가 롯데아이몰
  발주건 자체가 아직 목록에 없다.
  - 맞지 않는 태그는 점수를 더하지 못하면서 **후보 행마다 주문번호 칸 전체를 문자열로 만드는
    비용만** 늘린다 (아래 실측). 어떤 표기가 붙는지 확인되면 `extract()` 반환값에 한 줄만
    추가하면 된다.
- 표(`table`)가 셋인데 **클래스가 셋 다 `table_Ninfo` 로 같다** (배송지 정보 / 주문고객정보 /
  결제상세 정보). 구분되는 건 `<caption>` 뿐이라 그걸로 고른다. 수령인을 배송지 표 안에서만
  찾는 것도 이 때문이다 — 같은 페이지의 `주문하시는 분`(계정 주인)과 섞이면 안 된다.
- 버튼은 상단 `주문번호 : … [인터넷]` 의 **`[인터넷]` 뒤**에 붙인다. 바깥 `p.txt` 에 붙이면
  블록이라 줄이 바뀐다.
- 값도 버튼 자리도 **서버가 내려준 최초 HTML 에 이미 다 들어 있다** (`.Nodview_di1`·`.totalN`·
  `caption`·`paynoti_txt` 모두 확인). 그래서 `place()` 가 첫 호출에 성공하고
  **`MutationObserver` 도 10초 폴백 타이머도 아예 만들어지지 않는다.**

### 더현대Hi

- **결제금액은 `승인금액`, 결제일시는 `승인일시`** — 둘 다 아래쪽 `결제수단 & 승인내역` 블록에서
  읽는다. 위 `결제정보` 의 `총 결제 금액` 과 값이 같아 보여도, 신고 기준은 실제로 승인이 떨어진
  금액이라 그쪽에서 읽는다.

  ```
  결제정보                        결제수단 & 승인내역
    상품금액       10,000원         네이버페이   10,590원
    할인금액       -2,000원         H.Point         410원
    판매금액        8,000원         승인일시   2026.08.27 07:42:09
    배송비          3,000원         승인금액       10,590원
    포인트 사용       -410P
    총 결제 금액   10,590원
  ```

  - 승인 블록은 결제수단마다 붙으므로 **합산**한다. H.Point 처럼 승인 블록이 없는 수단은 자연히
    빠지는데, 롯데온에서 L.POINT, SSG 에서 SSG MONEY 를 빼는 규칙과 결이 같다.
  - 금액은 **부호를 살려** 더한다. 취소 승인이 `-28,000원` 으로 붙는 자리가 있어서(`결제정보
    변경 내역` 이 그렇다) 절댓값으로 더하면 취소분이 매입처럼 보태진다. 빼는 쪽으로 두면 합이
    0 이하가 되어 오류로 잡힌다.
  - **취소된 주문에는 `결제수단 & 승인내역` 섹션이 아예 없다** (`환불 정보` 가 대신 붙는다).
    승인금액을 못 찾아 그대로 멈추는데, 취소건은 어차피 보낼 게 아니라 손대지 않았다.

  눌러서 다시 여는 주소라, **지금 주소의 `ecOrdTypCd` 를 그대로 물려서** 만든다.
- **구입금액은 결제금액 아래 줄들의 `원` 항목 합이다 — 포인트는 뺀다.**

  ```
  결제정보
    결제금액        25,465원      <- 총액. 망고 행 매칭 보조키(total)로만 쓴다
    네이버페이      25,417원      <- 실제로 빠져나간 돈 = 구입금액
    GS ALL 포인트       48P       <- 더하지 않는다
  ```

  - 총액 25,465 = 25,417 + 48P 다. 롯데온의 L.POINT, SSG 의 SSG MONEY, CJ온스타일의 `P` 항목을
    빼는 것과 같은 규칙이고, 판별도 같은 자리에서 한다 — 금액 뒤 단위가 `원` 인 줄만 더한다.
  - 첫 줄(`결제금액`)은 합에서 뺀다. 그러지 않으면 총액을 두 번 세게 된다. 줄을 자리(첫 번째)나
    클래스(`.title_option`)가 아니라 **라벨 이름**으로 골라내므로, 결제수단이 여럿이라 줄이
    늘어나거나 순서가 바뀌어도 같은 값이 나온다.
- **확인한 건 한 건뿐이다.** 주문목록 화면의 주소를 찾지 못해(`dlvCurStaList.gs`·`dlvCurSta.gs`
  둘 다 오류 페이지) 다른 마켓처럼 최근 수십 건을 훑어보지 못했다. 결제수단이 둘 이상인 주문건,
  배송지가 여럿인 주문건은 아직 눈으로 보지 못했다는 뜻이다 — 값이 어긋나면 토스트에 결제정보
  블록이 통째로 찍히므로 그걸 보고 규칙을 고치면 된다.
- **결제일시가 없다. 주문일뿐이다.** 머리글의 `주문일 : 2026.08.28 | 주문번호 : 3469850976`
  한 줄이 전부다. 롯데온·SSG·패션플러스·롯데아이몰·CJ온스타일·NS몰과 같이 날짜만 넘긴다.
  - 주문일에는 점이 있고 주문번호에는 없어서 날짜 정규식 하나로 둘이 섞이지 않는다.
- **주문번호 표기가 하나다.** 화면도 주소(`ordNo`)도 `3469850976` 으로 같다 — SSG·롯데아이몰·
  CJ온스타일처럼 되돌릴 일이 없다. 값은 주소에서 읽고, 화면 쪽 번호는 **버튼 자리를 고르는 데**만
  쓴다 (그 번호가 찍힌 `span` 뒤에 붙인다).
- **수령인이 마스킹되지 않는다.** `받으시는 분` 칸이 `김형식 / 010-2977-8032 /` 라 첫 `/` 앞이
  이름이다. 배송지가 여럿이면 이 칸도 여럿이므로 **첫 배송지**의 받는사람을 쓴다
  (CJ온스타일·NS몰과 같은 결정).
- **발주처 태그(`marketTag`)를 넘기지 않는다** — 지마켓·패션플러스·롯데아이몰·더현대Hi·
  CJ온스타일·NS몰과 같은 사정. 망고 발주처 슬롯은 도메인 꼴로 찍히는데 GS SHOP 발주건이 아직
  목록에 없어 어떤 표기가 붙는지 확인하지 못했다.
- 버튼은 머리글의 주문번호 **뒤**에 붙는다. `p.order_txt_area2` 가 `right: 0` 으로 붙어 있어
  버튼이 붙으면 오른쪽으로 넘치지 않고 **왼쪽으로 늘어난다** (창을 좁혀도 잘리지 않는다).

### 옥션

- **주문상세정보는 목록 위에 뜨는 레이어 안의 iframe 이다.** 주문내역조회의 [주문상세보기] 는
  `InProcessAction.PopupOrderDetail(주문번호)` 를 불러 `iframe#ifContentsid` 에 아래 주소를 넣는다.

  ```
  https://escrow.auction.co.kr/Close/OrderProcessDetailLayer.aspx?order_no=<주문번호>
  ```

  그래서 이 확장에서 **처음으로** `all_frames: true` 를 쓴다. 매칭 주소가 이 문서 하나뿐이라
  목록 화면에는 아무것도 주입되지 않는다 (위 성능 절). 주소를 직접 열어도 같은 문서라 그대로
  동작하고, 간단메모에 넣는 URL 이 바로 그 주소다.
- **레이어를 다시 열면 문서를 새로 읽는다.** iframe 의 `src` 가 매번 다시 설정되므로 content
  script 도 다시 주입된다. 무신사·NS몰처럼 라우트를 지켜볼(`watch`) 이유가 없다.
- **구입금액은 결제정보의 `신용카드` 줄이다.**

  ```
  결제정보
    최종 결제금액    31,650원      <- 망고 행 매칭 보조키(total)로만 쓴다
    신용카드         31,650원      <- 구입금액. tr.sub = 결제수단 내역
      현대카드/일시불(무이자)
    상품금액         38,500원      <- tr.sep. 여기부터는 금액 내역이라 더하지 않는다
    쿠폰할인금액     -3,000원
    즉시할인금액     -3,850원
  ```

  결제수단 줄만 `tr.sub` 로 따로 표시돼 있어서 그중 이름에 `카드` 가 든 줄을 더한다.
  스마일캐시·스마일페이가 섞이면 그만큼 빠진다 — 롯데온의 L.POINT, SSG 의 SSG MONEY,
  GS SHOP 의 포인트 줄을 빼는 것과 같은 규칙이다.
  - **최근 75건은 전부 `신용카드` 한 줄뿐이었다** (2026-08-31 확인). 다른 수단만으로 결제한
    건이 나오면 금액이 0이 되어 토스트에 결제정보 표가 통째로 찍힌다.
- **배송비를 더해 금액을 조립하지 않는다.** 상품 줄의 배송비가 `배송비` 면 최종 결제금액에
  들어 있고(29,900 + 3,000 − 5,090 = 27,810), `추가 배송비` 면 들어 있지 않다
  (39,000 + 6,000 − 3,750 − 7,800 = 33,450 인데 카드는 27,450). 75건 중 8건이 뒤쪽이다.
  어느 쪽이든 실제로 카드로 빠져나간 돈은 `신용카드` 줄이라, 그 줄을 그대로 쓴다.
- **한 결제에 상품이 둘일 수 있다** (75건 중 6건). 그때 레이어는 두 상품을 모두 보여주고
  상품마다 주문번호가 따로다. 망고 행도 상품마다 따로이므로 **버튼을 상품마다** 붙인다
  (지마켓과 같은 결정, `key` 는 `au0`·`au1`).
  - 카드 금액은 결제 전체의 금액이라 그때는 그 상품 줄의 **상품금액 + 할인금액**을 쓴다
    (47,200 − 13,975 = 33,225). 배송비 칸은 상품 줄 전체에 rowspan 으로 걸려 있어 어느 상품의
    몫인지 알 수 없으므로 빼는데, 빼고 더한 합이 카드 금액과 어긋나고 **넣으면 맞는** 경우에만
    그 줄에 붙인다. 확인된 3건(66,450 / 77,510 / 80,040) 모두 나눈 합이 카드 금액과 정확히 맞다.
- **버튼은 상품명 칸에 붙는다.** 주문번호가 찍힌 첫 칸은 표 너비의 13%(99px)뿐이라 버튼을 넣으면
  세 줄로 접힌다 (실측 66×57px). 상품명 칸은 `width:auto` 라 236px 이고, 버튼이 들어가도
  팝업이 가로로 넘치지 않는다 (문서 폭 900px 그대로).
- **오래된 주문건은 받는 분 이름이 가려진다.** `허*식` 꼴이고, 75건 중 **63건**이 그랬다
  (대체로 3주보다 오래된 건이다). 마스킹 전 이름은 화면에도 응답 HTML 어디에도 없다 —
  더현대Hi 처럼 RSC 페이로드에서 되살릴 수가 없어서, **보내기 전에 끊고 이유를 알려준다.**
  그대로 보내면 망고에서 아무 행도 잡히지 않는다.
  - 갓 주문한 건은 가려지지 않으므로 이 확장을 쓰는 흐름(주문하고 바로 옮기기)에서는 걸리지 않는다.
- **결제일시가 없다. 주문일자뿐이다.** 머리글의 `결제번호 : 1721641692 | 주문일자 : 2026년 08월 24일`
  한 줄이 전부다. 롯데온·SSG·패션플러스·롯데아이몰·CJ온스타일·NS몰·GS SHOP 과 같이 날짜만 넘긴다.
  - 상품 줄의 [신용카드영수증 출력]은 `accounting.auction.co.kr` 로 넘어가는 별도 창이다.
    거기에 승인일시가 있을 수 있지만, 무신사 영수증처럼 **백그라운드 탭을 띄워야** 읽을 수 있는
    구조라 열지 않았다 — 롯데온과 같은 결정이다.
- **망고에 넣는 주문번호는 `결제번호` 가 아니라 `주문번호` 다.** 머리글에 찍힌 것은 결제번호
  (`1721641692`)이고, 상품 줄 첫 칸의 괄호 안(`(2569178034)`)이 주문번호다. 주소의
  `order_no` 와 같은 값이라 어느 쪽으로 열어도 같다.
- **페이지 인코딩이 EUC-KR 이다.** content script 는 브라우저가 이미 디코드한 DOM 을 읽으므로
  상관없지만, 콘솔에서 `fetch(...).then(r => r.text())` 로 받아 보면 글자가 깨진다. 그때는
  `arrayBuffer()` 로 받아 `new TextDecoder('euc-kr')` 로 풀 것.
- **배송지는 75건 모두 하나였다.** 여럿인 주문건은 아직 보지 못했다는 뜻이다 —
  CJ온스타일·NS몰·GS SHOP 처럼 첫 배송지의 받는사람을 쓰게 되어 있다.
- **발주처 태그(`marketTag`)를 넘기지 않는다** — 지마켓·패션플러스·롯데아이몰·더현대Hi·
  CJ온스타일·NS몰·GS SHOP 과 같은 사정. 옥션 발주건이 아직 망고 목록에 없어 어떤 표기가 붙는지
  확인하지 못했다.

### 현대몰

- **주문상세는 별도 주소 한 장이다** (`www.hmall.com/mo/mpa/selectOrdPTCPup?ordNo=...`).
  주소만 있으면 그대로 열리고, 간단메모에 넣는 URL 이 바로 그 주소다.
- **목록에서 눌러 들어가면 문서를 다시 읽지 않는다.** 마이페이지의 [주문/배송 상세] 는
  클라이언트 이동이다 (표식을 심어 두고 눌러 보니 표식이 살아남고 navigation 이름은 여전히
  마이페이지였다 — 실측). 그래서 팝업 주소만 매칭했을 때는 **새로고침해야 버튼이 나왔다.**
  매칭을 `/mo/*` 로 넓히고 `watch: true` 를 켜서 라우트를 따라가게 했다 (위 성능 절).
  - 사이트 전체가 아니라 `/mo/*` 인 이유는 SPA 경계가 거기까지라서다 — 홈(`/md/*`)에서
    `/mo/*` 로 들어가는 길은 전부 문서를 다시 읽는다 (실측).
- **HTML 에는 마크업이 없고 `__NEXT_DATA__` 만 있다.** 그래서 GS SHOP 처럼 주소를 fetch 해
  문자열을 뒤지는 방법이 통하지 않는다. 반대로 값을 XHR 로 따로 받지도 않아서, 화면은
  하이드레이션(238ms) 한 번에 통째로 그려진다.
- **그런데도 `__NEXT_DATA__` 가 아니라 화면을 읽는다.** 이 페이지는 `gssp: true` — 서버에서
  props 를 만들어 내려주는 페이지다. 그런 페이지로 **클라이언트 이동**하면 Next.js 는
  `/_next/data/<buildId>/…json?ordNo=…` 만 받아 화면을 갈아끼우고, 문서에 박힌
  `__NEXT_DATA__` 는 **처음 읽은 문서 것 그대로 남는다.** 있을 수 있는 일이 아니라 실제로
  그랬다 — 마이페이지에서 눌러 들어간 화면에서 `__NEXT_DATA__.page` 가
  `/mpf/selectMyPageMain` 인 채로 화면은 주문 `20260829059262` 를 그리고 있었다 (실측).
  그 페이로드를 믿었으면 마이페이지 것을 보냈을 것이다. 더현대Hi 에서 A 의 수령인을 B 의
  주문번호와 함께 보낼 뻔했던 함정과 같고, 화면에는 그 함정이 없다.
- **구입금액은 결제/취소내역의 `원` 항목 합이다 — 포인트는 뺀다.**

  ```
  결제정보                       결제/취소내역
    주문금액       18,900원        [결제] 2026. 08. 25
    할인금액   (-)  3,250원          H.Point         270P    <- 더하지 않는다
    쿠폰할인        1,890원          네이버페이   15,380원    <- 구입금액
    네이버가격비교  1,360원
    결제금액       15,650원   <- 총액. 망고 행 매칭 보조키(total)로만 쓴다
  ```

  - 총액 15,650 = 15,380 + 270P 다. 왼쪽 `결제금액` 에는 포인트가 섞여 있어 쓰지 않는다.
    롯데온의 L.POINT, SSG 의 SSG MONEY, GS SHOP 의 GS ALL 포인트를 빼는 것과 같은 규칙이고,
    판별도 같은 자리에서 한다 — 금액 뒤 단위가 `원` 인 줄만 더한다.
  - 신용카드로 결제한 주문이면 그 줄이 `신용카드 15,380원` 으로 찍혀 그대로 잡히고,
    네이버페이·상품권처럼 카드가 아닌 실결제 수단도 같은 자리에서 같은 꼴로 잡힌다.
  - `[결제]`·`[취소]` 는 **묶음 머리글**이다. 한 묶음에 수단이 여럿이면 두 번째 줄부터는
    머리글이 빈 `<p></p>` 로 붙으므로, 머리글을 만날 때 부호를 정해 두고 그 뒤 줄들에 그대로
    적용한다. 취소분은 빼는 쪽이라 전액 취소된 주문은 합이 0이 되어 오류로 잡힌다 —
    취소건은 어차피 망고에 보낼 게 아니라 그대로 둔다 (더현대Hi 와 같은 결정).
- **확인한 건 두 건이다.** 포인트가 섞인 건(`H.Point 270P` + `네이버페이 15,380원` → 15,380)과
  카드 한 건(`신용카드 60,791원` → 60,791)이다. 결제수단이 둘 이상인 주문건, 배송지가 여럿인
  주문건, 부분취소된 주문건은 아직 눈으로 보지 못했다 — 값이 어긋나면 토스트에 결제/취소내역과 배송지 블록이
  통째로 찍히므로 그걸 보고 규칙을 고치면 된다.
- **결제일시가 없다. 날짜뿐이다.** `[결제] 2026. 08. 25` 가 전부다. 점 뒤에 공백이 있어 다른
  마켓과 같은 정규식으로는 안 잡히므로 공백을 허용해 읽고 `2026.08.25` 꼴로 맞춘다. 머리글
  (`p.date`)의 주문일도 같은 날짜라 폴백으로 둔다. 롯데온·SSG·패션플러스·롯데아이몰·
  CJ온스타일·NS몰·GS SHOP·옥션과 같이 날짜만 넘긴다.
- **주문번호 표기가 하나다.** 화면도 주소(`ordNo`)도 `20260825023493` 으로 같다 —
  SSG·롯데아이몰·CJ온스타일처럼 되돌릴 일이 없다.
- **수령인이 마스킹되지 않는다.** 배송지 블록의 `h4` 가 이름 한 칸이다 (`공은하`).
  배송지가 여럿이면 이 블록도 여럿이므로 **첫 배송지**의 받는 분을 쓴다
  (CJ온스타일·NS몰·GS SHOP·옥션과 같은 결정).
- **`article payment-info` 가 둘이다** (결제정보 · 결제/취소내역). 자리(첫 번째/두 번째)로
  고르지 않고 `h3` 글자로 가려낸다 — 할인이 없는 주문에서 블록이 하나만 남아도 같은 값이 나온다
  (GS SHOP 에서 목록 둘을 가려낸 것과 같다).
- **버튼은 결제/취소내역이 그려졌을 때만 붙는다.** 머리글과 결제내역이 한 번에 함께 그려지므로
  이 조건이 늦추는 것은 없고, 대신 **버튼이 보이면 값도 있다**는 성질이 생긴다
  (CJ온스타일에서 저절로 성립했던 성질을 여기서는 조건으로 만든다).
  - 머리글 `.number` 가 flex 라 버튼이 주문번호와 **같은 줄**에 들어간다.
- **발주처 태그(`marketTag`)를 넘기지 않는다** — 지마켓·패션플러스·롯데아이몰·더현대Hi·
  CJ온스타일·NS몰·GS SHOP·옥션과 같은 사정. 현대몰 발주건이 아직 망고 목록에 없어 어떤 표기가
  붙는지 확인하지 못했다.

### 망고

- 망고 목록 페이지는 `Array.prototype.find`가 정상 동작하지 않는다. 확장은 격리된 컨텍스트에서
  실행되어 영향받지 않지만, 콘솔에서 직접 스크립트를 돌릴 때는 `.filter(...)[0]`을 쓸 것.

### 마켓 추가하기

`common.js` 가 버튼·토스트·전송을 다 맡으므로, 사이트 스크립트는 두 가지만 내놓으면 된다.

```js
window.__LM_SITE__.mount({
  extract, // () => { url, orderNo, price, payDate, receiver, total, marketTag } | { error }
  anchor,  // () => 버튼을 옆에 붙일 요소 (없으면 우측 하단 고정 버튼으로 폴백)
  watch,   // (선택) SPA 면 true — 라우트가 바뀌어도 버튼을 따라 붙인다
  key,     // (선택) 한 화면에 버튼이 여럿일 때 자리 구분자 (지마켓: 상품마다 'gm0','gm1'…)
});
```

`marketTag` 는 문자열 또는 배열이다.

#### `key` — 한 화면에 버튼이 여러 개

버튼은 `data-lm-key` 를 달고 붙는다. `place()` 가 껍데기(아래 `watch` 설명)를 걷어낼 때 **같은
`key` 인 것만** 지우므로, 지마켓처럼 자리가 여럿이면 옵저버들이 서로의 버튼을 지우고 다시 붙이는
일이 없다. `key` 를 주지 않으면 `'default'` 라 예전과 똑같이 동작한다.

지마켓은 자리(index)로 mount 해 두고 그 자리에 지금 있는 상품을 그때그때 읽는다. 상품이 더 많은
주문을 열면 모자란 만큼 mount 를 더 붙이고, 적은 주문에서는 남는 자리의 `anchor()` 가 `null` 을
줘서 버튼이 떨어진다.

옥션도 같은 방식인데 `watch` 가 없다 (레이어를 다시 열면 문서를 새로 읽는다). 그래도 자리가
여럿일 수 있어 `key` 는 필요하다 — `anchor()` 안에서 상품 줄을 다시 세고 모자란 만큼 mount 를
더 붙이므로, 첫 `place()` 한 번에 상품 수만큼 버튼이 붙는다 (`au0`, `au1`).

#### `watch` — SPA 대응

무신사·네이버페이·지마켓·더현대Hi·NS몰·현대몰 은 주문목록에서 주문상세로 **문서를 다시 읽지 않는다**. content script 는 그때
다시 주입되지 않으므로, 버튼을 한 번 붙이고 끝내면 라우트가 바뀌는 순간 사라진다.

`watch` 는 SPA 전용이 아니다. 패션플러스처럼 **페이지가 우리 버튼을 통째로 다시 그리는**
경우(Vue 마운트)도 같은 장치로 잡는다 — 버튼이 갈려 나갔다는 사실은 둘 다 똑같기 때문이다.

`watch: true` 면 `MutationObserver` 를 끊지 않고(여전히 150ms 에 한 번) 매 틱마다

- `anchor()` 가 요소를 주면 그 옆에 (이미 그 자리면 아무것도 안 하고) 붙이고,
- `null` 을 주면 — 주문상세가 아닌 화면이라는 뜻이라 — 버튼을 떼어낸다.

매 틱 `anchor()` 를 부르므로 **캐시는 사이트 스크립트 몫이다.** `musinsa.js`·`naver.js`·`fashionplus.js`·`hmall.js` 는 찾은 요소를
들고 있다가 `isConnected` 와 현재 주문번호만 확인하고 돌려준다. 캐시가 살아 있는 동안
문서를 훑는 비용은 0이고, 라우트가 바뀐 틱에만 다시 찾는다.
`nsmall.js` 는 클래스 이름이 사람이 붙인 것이라 캐시가 식어도 선택자 하나(0.0006 ms)면 끝난다.
`gmarket.js` 는 자리가 여럿이라 조금 다르다 — 클래스 선택자 한 번(`button.button-copy`)이면
전부 찾으므로 결과를 100ms 동안 공유한다. 상품 수만큼 도는 옵저버가 같은 틱에 문서를 여러 번
훑지 않게 하는 것이 목적이다.

`extract` 는 `await` 되므로 비동기여도 된다. 새 사이트는 `manifest.json` 의
`host_permissions` 와 `content_scripts` 에 한 줄씩 추가하면 끝이다.
