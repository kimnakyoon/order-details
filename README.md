정보를 옮기고 주문상태를 `배송완료`로 바꿔 저장합니다.

## 설치

1. Chrome 주소창에 `chrome://extensions` 입력
2. 우측 상단 **개발자 모드** 켜기
3. **압축해제된 확장 프로그램을 로드합니다** 클릭
4. `C:\Users\admin\workspace\kny\mango\order-details\extension` 폴더 선택

> 이미 설치되어 있다면 `chrome://extensions` 에서 **새로고침(⟳)** 을 누른 뒤
> 마켓·망고 탭을 각각 새로고침해야 변경이 반영된다.

### 계정이 여러 브라우저에 흩어져 있다면 (릴레이)

무신사 계정이 셋이라 크롬·웨일·엣지에 하나씩 로그인해 두는 경우다. **확장은 브라우저마다
완전히 격리되어**, 웨일에 설치한 확장의 `chrome.tabs` 로는 크롬의 망고 탭을 볼 수 없다.
(크롬 프로필을 나눠도 마찬가지다.) 그래서 사이에 루프백 서버 하나를 둔다.

1. 세 브라우저 **모두**에 같은 `extension` 폴더를 로드한다
   - 웨일 `whale://extensions` · 엣지 `edge://extensions` — 둘 다 크로미움이라 그대로 붙는다
2. 릴레이를 띄운다 — 둘 중 하나
   - **로그온할 때 자동으로** (권장): `relay\install-startup.vbs` 를 더블클릭한다.
     시작프로그램에 등록되어 다음 로그온부터 **창 없이** 뜬다. 해제는 `uninstall-startup.vbs`.
   - **그때그때 손으로**: `relay\start.cmd` 를 더블클릭한다 (창을 닫으면 멈춘다).
3. 끝. 어느 브라우저가 보내는 쪽인지 **설정할 것이 없다.**

> 자동 실행은 **현재 사용자 로그온 시**로 등록된다 (관리자 권한 불필요).
> 등록되는 파일은 `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\mango-relay.lnk`
> 하나뿐이고, 그게 `relay-hidden.vbs` → `run-hidden.cmd` → `node relay.js` 를 창 없이 띄운다.
> 창이 없으므로 로그는 `relay
elay.log` 에 쌓인다 (부팅마다 새로 쓴다).
> 폴더를 옮기면 바로가기가 끊기니 `install-startup.vbs` 를 다시 실행할 것.

## 사용법

1. **망고 주문관리 탭에 해당 주문건을 띄워 둔다** (이게 전제다)
2. 주문상세 페이지를 연다
   - 롯데온 `.../p/order/claim/orderDetail?odNo=...`
   - SSG `pay.ssg.com/myssg/orderInfoDetail.ssg?orordNo=...`
   - 무신사 `www.musinsa.com/order/order-detail/...`
   - 네이버페이 `orders.pay.naver.com/order/status/...`
   - 패션플러스 `www.fashionplus.co.kr/mypage/order/detail/...`
3. **주문번호 옆의 🥭 망고로 전송** 버튼 클릭
4. 값 입력 + 주문상태 변경 + 해당 행 체크 → **선택수정**까지 자동 클릭되고
   `수정하시겠습니까?` 확인창도 자동 승인되어 **저장까지 완료**된다

> 확장은 **이미 열려 있는 망고 탭에서만** 처리한다. 목록에 그 주문건이 없으면
> 값을 넣지 않고 그대로 멈춘다. 망고 탭을 대신 검색·이동시키지 않는다.

웨일·엣지처럼 **망고 탭이 없는 브라우저**에서 누르면, 값이 릴레이로 넘어가고
`넘겼습니다. 망고 탭이 열려 있는 크롬 창을 띄우면 반영됩니다` 라고 뜬다.
그 뒤 **크롬 창을 띄우는 순간** 크롬 쪽 확장이 가져가 반영·저장하고 알림을 띄운다.

## 주문건 매칭 방식

마켓의 **받는 분** 이름으로 망고 목록에서 후보를 찾고, 아래로 점수를 매겨 1건을 고른다.

- 이미 같은 주문번호가 들어있는 행 → 즉시 선택 (재전송)
- 총 결제금액 일치 (+4) / 같은 발주처 태그 (+2) / 상품주문번호 비어있음 (+1) / 상태가 결제완료 (+1)
- 반품·교환·취소완료 상태 (−5), 그리고 이 상태의 행은 값을 덮어쓰지 않고 중단

발주처 태그는 사이트 스크립트가 `marketTag` 로 넘긴다 — 롯데온은 `LOTTEON`, SSG는 `SSG.com`
(망고 목록 행에 `[SSG.com] 아이더 남성 …` 처럼 찍힌다). 문자열 대신 **배열**을 넘기면
그중 하나만 걸려도 인정한다 — 무신사는 표기를 확인하지 못해 `['무신사', 'MUSINSA']` 로 둔다.

동점 후보가 2건 이상이면 자동 입력하지 않고, 망고 화면에서 후보 행을 주황색으로 표시하고
**[여기에 적용]** 버튼을 띄운다.

## 안전장치

- 저장 직전 **모든 체크박스를 해제**한 뒤 대상 행만 체크한다 (선택수정이 다른 행까지 건드리는 것 방지)
- 동점 후보가 2건 이상이면 자동 입력·저장을 하지 않고 사용자에게 선택을 요구한다
- 반품/교환/취소완료 상태의 행은 값을 덮어쓰지 않고 중단한다

> 확인창 없이 바로 저장되므로 되돌리기가 없다. 매칭이 어긋나면 그대로 저장된다는 뜻이라,
> 위 세 가지가 유일한 방어선이다.

## 망고 페이지 성능

망고를 쓰는 동안 확장이 아무 부하도 주지 않도록, **망고 페이지에는 상주하는 코드가 없다.**

- `manifest.json` 의 `content_scripts` 는 마켓 주문상세 페이지에만 걸려 있다.
  망고 목록 페이지를 열고 검색하고 스크롤하는 동안 확장 코드는 한 줄도 실행되지 않고,
  CSS 도 주입되지 않는다.
- 마켓에서 전송 버튼을 누른 순간에만 `background.js` 가 `chrome.scripting.executeScript` 로
  `mango_main.js`(MAIN) 와 `mango.js`(ISOLATED) 를 주입하고 `__LM_MANGO__.run(payload)` 를 호출한다.
  두 스크립트 모두 자체 가드가 있어 재주입해도 한 번만 초기화된다.
- 후보 선택 UI 의 CSS 도 후보가 2건 이상일 때만 `<style>` 로 주입한다.

### 주입된 뒤의 스캔 비용

망고 목록 한 행은 **요소 345개 / `textContent` 3,896자**나 된다. 그중 절반(1,845자)은
트래킹번호 칸에 들어있는 `<style>` 블록과 택배사 `<select>` 옵션 목록인데, 매칭에는
전혀 쓰이지 않는다. 반면 **수령인 칸은 26자**뿐이다.

그래서 후보 판정을 두 단계로 나눈다.

1. **수령인 칸만** 읽어 거른다 — 행 전체의 1/150. 대부분의 행이 여기서 끝난다.
2. 살아남은 소수의 행만 결제금액·주문번호 칸을 마저 읽는다.

칸 위치는 헤더 텍스트(`수령인`, `결제금액`, `주문번호`)에서 한 번만 찾는다. 순서가 바뀌어도
따라가고, 못 찾으면 행 전체 텍스트로 폴백해 동작은 유지한다.

50행 목록에서 실측한 값 (Chrome, 50회 평균):

| 상황 | 기존 | 현재 |
|---|---|---|
| 일치 0건 (가장 흔함) | 0.89 ms | **0.056 ms** |
| 50행 전부 일치 (최악) | 1.01 ms | **0.25 ms** |

바꾸기 전후로 후보 목록과 점수가 완전히 같은 것을 같은 페이지에서 확인했다.

### 한 번 보낼 때 망고 페이지에서 쓰는 시간

같은 50행 목록(요소 16,835개 · 클릭요소 1,543개)에서 실측한 값이다.

| 단계 | 예전 | 지금 |
|---|---|---|
| 행 스캔 (일치 0건) | 0.056 ms | 0.056 ms |
| 값 쓰기 — 이벤트 dispatch + 체크 해제 | 0.42 ms | **0.003 ms** |
| 간단메모 칸 찾기 | 0.053 ms | **0.002 ms** |
| [선택수정] 버튼 찾기 | 0.485 ms | **0.010 ms** |
| `clearPicker` (후보 UI 를 띄운 적 없을 때) | 0.028 ms | **0 ms** |
| **합계** | **약 1.04 ms** | **약 0.08 ms** |

그리고 이건 **버튼을 누른 그 한 번**에만 드는 비용이다. 망고를 그냥 쓰는 동안에는
여전히 확장 코드가 한 줄도 실행되지 않는다.

#### 이제 어느 단계도 레이아웃을 읽지 않는다

위 표의 숫자보다 중요한 성질이다. `offsetParent`·`getBoundingClientRect`·`innerText` 는
**강제 리플로우**라, 요소 1.7만 개짜리 이 페이지에서는 브라우저가 마침 레이아웃을 다시 계산해야
하는 상태일 때 비용이 몇 배로 튄다. 평균값만 보면 안 보이고, 사용자가 뭔가 하던 중에 눌렀을 때만
느껴지는 종류의 비용이다.

마지막까지 남아 있던 곳이 간단메모 칸 고르기였다 (보이는 칸만 남기려 `offsetParent`, 화면 순서로
정렬하려 `getBoundingClientRect().y`). 셀 안에서는 **DOM 순서가 곧 화면 순서**라(50행 전부 확인)
숨은 저장칸만 걸러내면 같은 결과가 나온다.

| 간단메모 칸 고르기 | 레이아웃 깨끗할 때 | 레이아웃 더러울 때 |
|---|---|---|
| `offsetParent` + `getBoundingClientRect` | 0.014 ms | **0.065 ms** |
| DOM 순서만 | 0.002 ms | **0 ms** |

전체 경로(스캔 + 메모 + 선택수정 버튼 + 체크 해제)를 레이아웃을 일부러 더럽혀 가며 돌려도
깨끗할 때와 차이가 없다 (0.10 ms / 0.07 ms). 리플로우가 남아 있으면 여기서 몇 배로 벌어진다 —
망고 화면 구조를 건드릴 때 이 측정을 다시 해 보면 된다.

`showPicker()` 의 `scrollIntoView` 는 예외로 남겨 뒀다. 후보가 2건 이상일 때만 도는 데다,
그건 성능이 아니라 사용자에게 후보를 보여주려는 동작 자체다.

### 값을 쓸 때 이벤트를 쏘지 않는다

한 번 보낼 때 확장이 망고 페이지에서 하던 일의 **절반이 이벤트 dispatch 15발**이었다
(입력칸 4개 × `input`·`change`·`keyup`, 그리고 체크 해제마다 `change`).

망고 화면을 열어 핸들러를 직접 확인한 결과, 우리가 건드리는 칸에 붙어 있는 건 jQuery 로
걸린 것 하나씩뿐이었다.

| 칸 | 걸린 이벤트 | 하는 일 |
|---|---|---|
| `uid_usd_order_num` · `uid_usd_order_price` · `uid_usd_delivery_num` | `keyup` | **그 행의 체크박스를 켠다** |
| `uid_state` (주문상태) | `change` | 같음 |
| `uid_check[]` (체크박스) | — | 핸들러 없음 |
| 간단메모 칸 (`.msp-*`) | — | 핸들러 없음 (**단, 아래 단서**) |

`input` 은 어디에도 걸려 있지 않고, 핸들러의 효과(행 체크)는 **`apply()` 가 곧바로 덮는다** —
어차피 전체 체크를 풀고 대상 행만 다시 켜기 때문이다. 저장을 맡는
`really_all_select_modify()` 도 체크된 행의 값을 id 로 `.val()` 해서 읽어 JSON 으로 싣고
`submit()` 할 뿐, '수정됨' 표시 같은 건 보지 않는다.

그래서 이벤트를 전부 뺐다. dispatch 15발과, 그중 `keyup`/`change` 핸들러가 부르는
**문서 전체 jQuery 조회 4번**이 같이 사라진다. (`click` 은 원래도 쓰지 않는다 — 체크 상태가
다시 뒤집힌다.)

> 망고 화면이 바뀌면 이 전제도 바뀔 수 있다. 확인 방법은
> `jQuery._data(document.getElementById('uid_usd_order_num_<uid>'), 'events')`.

#### 간단메모만은 예외다 — 숨은 칸을 직접 다시 만든다

간단메모 칸에는 **저장되는 값과 화면에 보이는 칸이 따로 있다.** 다른 네 칸은 우리가 쓰는
요소가 곧 저장되는 요소지만(`uid_usd_order_num_<uid>` 등 id 로 `.val()` 해 간다), 메모는
저장되는 값이 숨어 있는 `uid_usd_memo_<uid>`(`name="uid_usd_memo[]"`) **하나**뿐이고,
보이는 입력칸 3개는 그 값을 줄 단위로 쪼개 놓은 편집 UI 다.

```
uid_usd_memo_<uid>  =  비어 있지 않은 보이는 칸들을 '
' 로 이은 것
```

사람이 타이핑하면 사이트 핸들러가 세 칸을 도로 합쳐 숨은 칸에 넣는데, 이벤트를 빼면서
그 합치기가 돌지 않게 됐다. 증상이 조용하다 — **화면에는 URL 이 보이고 성공 토스트도 뜨는데
저장하고 나면 메모만 비어 있다.** 다른 값(주문번호·금액·결제일시·주문상태)은 멀쩡히 들어간다.

그래서 `writeMemo()` 가 보이는 칸에 쓴 뒤 위 규칙으로 숨은 칸을 직접 다시 만든다. 이벤트는
여전히 하나도 쏘지 않는다. (규칙은 망고 목록 50행 전부에서 확인했다.)

칸을 고를 때 레이아웃을 읽지 않는다 — 셀 안의 네 요소는 항상 `보이는 칸 3개 + 숨은 저장칸`
순서이고 DOM 순서가 곧 화면 순서다. 숨은 저장칸은 `uid_usd_memo_<uid>` 자기 자신으로 걸러낸다.
(위 '레이아웃을 읽지 않는다' 참고.)

### 그 밖의 절약

- **[선택수정] 버튼을 `onclick` 속성으로 한 번에 집는다.** 예전에는 `a`·`button`·
  `input[type=button]` **1,543개**를 돌며 `innerText` 를 읽어 라벨이 `선택수정` 인 것을 찾았다.
  요소마다 레이아웃을 강제하는 데다 0.49ms 다. `[onclick*="really_all_select_modify"]` 는
  0.01ms. 망고가 핸들러 이름을 바꾸면 예전 방식(단 `textContent`)으로 떨어진다.
- 행 스캔에 `innerText` 대신 `textContent` 를 쓴다 (`innerText` 는 행마다 레이아웃을 강제한다).
- `getBoundingClientRect` 를 쓰는 곳은 간단메모 칸 순서를 정하는 부분뿐이고,
  **매칭된 1개 행에서만** 호출한다. 게다가 **값을 쓰기 전에** 부른다 — 쓰고 나서 읽으면
  강제 리플로우가 걸린다 (0.007ms → 0.053ms).
- 후보 선택 UI 를 띄운 적이 **없으면** `clearPicker()` 는 문서를 훑지 않는다. `run()` 이
  시작할 때마다 무조건 부르는 자리라, 압도적으로 흔한 '한 방에 매칭' 경로에서 문서 조회
  3번이 통째로 사라진다.
- 체크 해제는 문서를 다시 훑지 않고 후보를 고를 때 모아둔 체크박스 목록을 재사용한다.
  선택수정이 읽는 값은 `uid_check[]` 뿐이라 그 목록이 곧 전부다.
- 망고 탭이 여러 개면 **사용자가 보고 있던 탭부터** 시도한다. 거기서 끝나면 나머지 탭에는
  스크립트를 주입조차 하지 않는다.
- 자동 저장 경로에서는 하이라이트·스크롤을 하지 않는다 (어차피 곧바로 페이지가 갱신된다).
- **주입 왕복 3번 → 2번.** `mango_main.js`(MAIN) 와 `mango.js`(ISOLATED) 는 서로를 기다릴
  이유가 없어 나란히 넣는다. 앞엣것은 `window` 리스너를 하나 걸어둘 뿐이고 그 리스너는
  저장 직전에야 불린다.
- 탭을 앞으로 가져올 때 `chrome.tabs.get` 을 다시 부르지 않는다. `chrome.tabs.query` 가
  `windowId` 를 이미 실어 준다.
- 발주처 태그 배열은 스캔 전에 **한 번** 만든다. 판정도 `some(화살표함수)` 대신 손으로 도는
  루프다 — 행마다 클로저를 만들지 않기 위해서다.
- 표(`<table>`)는 후보를 고를 때 찾아 둔 것을 저장 단계까지 들고 간다 (`closest` 재탐색 없음).

### 없앤 것 — 수령인 검색 이동

예전에는 열려 있는 탭에서 못 찾으면 수령인 이름으로 검색한 URL 로 망고 탭을 이동시켰다.
이게 확장에서 압도적으로 비싼 단계였다. 위의 스캔들이 0.05ms 단위인데, 목록 재로딩은
**초 단위**다 (요소 1.8만 개 + 서버 왕복). 게다가 사용자가 보던 목록·스크롤·체크 상태가 날아간다.

대상 주문건을 띄워 놓고 버튼을 누르는 흐름이라 그 왕복은 통째로 낭비여서 걷어냈다.
목록에 주문건이 없으면 아무것도 건드리지 않고 멈춘다. `searchUrl`·`waitForLoad`·`ymd`
함수도 같이 사라졌다.

### 마켓 페이지 쪽

- SSG는 버튼 자리를 찾을 때 **텍스트 노드를 훑는 빠른 경로**를 먼저 쓴다. 요소마다
  `textContent` 를 만드는 방식은 조상이 자손 텍스트를 다시 이어붙여 문서가 커질수록 비용이
  급격히 는다. 주문번호가 여러 요소로 쪼개진 경우에만 전수 조사로 넘어간다.
- 버튼 자리를 기다리는 `MutationObserver` 는 **150ms 에 한 번**으로 묶는다. 로딩 중
  DOM 변경마다 문서를 훑지 않기 위한 것이고, 보통 첫 시도에 이미 붙는다.

버튼을 붙일 자리를 기다리는 `MutationObserver` 는 프레임당 한 번으로 묶어 둔다.
SSG는 주문번호 요소를 찾느라 문서를 훑어야 해서, 로딩 중 변경마다 돌면 낭비다.

### confirm 자동 승인 방식

망고의 `really_all_select_modify()` 는 `confirm('수정하시겠습니까?')` 를 거친다.
콘텐츠 스크립트는 격리된 컨텍스트라 페이지의 `window.confirm` 을 바꿀 수 없으므로,
`mango_main.js` 를 `world: "MAIN"` 으로 **필요할 때 주입해** 페이지 컨텍스트에서 실행시킨다.
저장 직전 `LM_SUPPRESS_CONFIRM` 커스텀 이벤트를 쏘면 그 스크립트가 `window.confirm` 을
`() => true` 로 잠깐 바꾸고, 3초 뒤 원래대로 되돌린다. `alert` 은 건드리지 않으므로
망고가 내는 검증 오류 메시지는 그대로 보인다.

## 브라우저 사이 다리 (`relay/`)

의존성 없는 Node 서버 하나가 `127.0.0.1:8787` 에서 값을 잠깐 들고 있는다. 루프백에만 묶어서
같은 기기의 브라우저끼리만 닿는다.

| | 조건 | 하는 일 |
|---|---|---|
| 보내는 쪽 | 이 브라우저에 망고 탭이 **없다** | `POST /send` 로 넘기고 끝 |
| 받는 쪽 | 이 브라우저에 망고 탭이 **있다** | `GET /pending` → 반영 → `POST /ack` |

**역할을 설정하지 않는다.** 망고 탭이 열려 있는 브라우저가 곧 받는 쪽이다. 세 브라우저에
똑같은 폴더를 로드하면 각자 알아서 자기 역할을 한다.

### 왜 '창 포커스'가 신호인가

MV3 service worker 는 30초면 잠든다. 받는 쪽을 계속 깨워 두려면 WebSocket 을 물고 있거나
주기적으로 두드려야 하는데, 어차피 **결과를 보려면 크롬 창을 띄워야 한다.** 그래서
`chrome.windows.onFocusChanged` 를 신호로 쓴다.

- 상주 비용이 0이다. 크롬을 안 쓰는 동안 확장은 한 줄도 돌지 않는다.
- 사용자가 크롬으로 넘어오는 그 순간에 이미 반영돼 있다.
- 포커스 이벤트를 놓쳤거나 실패해서 남은 건은 **확장 아이콘을 눌러** 직접 밀어 넣는다.

망고 페이지에 상주 코드를 두지 않는다는 원칙도 그대로다 — 받는 쪽도 **반영할 게 실제로
있을 때만** 주입한다. 큐가 비어 있으면 `GET /pending` 에서 끝나고 망고 페이지는 건드리지도
않는다.

### 망고를 반복해서 긁지 않는다 — 실패는 자동 재시도하지 않는다

릴레이를 붙이면서 **확장이 망고를 느리게 만들 수 있는 경로가 딱 하나 생겼다.**

신호가 '창 포커스'인데, 반영 실패의 압도적 다수는 *그 주문건이 지금 목록에 없다* 이고
그건 사용자가 목록을 바꾸기 전까지 계속 실패한다. 막아두지 않으면 **창을 오갈 때마다**
망고 페이지에 스크립트를 주입하고 목록 전체를 훑게 된다. 알트탭 한 번에 한 번씩이다.

그래서 실패한 건의 id 를 적어 두고 `GET /pending?skip=…` 으로 넘긴다.

- 막힌 건은 **확장 아이콘을 눌렀을 때만** 다시 시도한다 (`drain(force)` 가 목록을 비운다).
- 뒤의 건들은 그대로 흘러간다. 한 건이 막혀도 큐 전체가 멈추지 않고, 큐 순서도 그대로다.
- 목록은 `chrome.storage.session` 에 둔다. service worker 가 30초마다 잠들어도 유지되고,
  브라우저를 닫으면 같이 사라진다 (다음에 켤 땐 상황이 바뀌었을 테니 한 번은 다시 해볼 만하다).

포커스 이벤트 자체도 **1.5초 안에 겹쳐 오면 무시한다.** 창을 몇 번 오갈 때마다 탭을 훑고
릴레이를 두드릴 이유가 없다. 그리고 `drain()` 은 **망고 탭이 있는지부터 확인하고 끝낸다** —
웨일·엣지는 이 한 줄 때문에 포커스가 바뀌어도 릴레이를 두드리지조차 않는다.

### 꺼낸다고 지우지 않는다

`GET /pending` 은 **맨 앞 것을 보여주기만** 하고, 받는 쪽이 실제로 반영에 성공해
`POST /ack` 를 보내야 큐에서 빠진다. 망고 목록에 그 주문건이 아직 없어서 실패하는 일이
흔한데, 그때 값을 잃으면 안 되기 때문이다. 목록을 맞춰 놓고 확장 아이콘을 다시 누르면 된다.

- 후보 동점이라 **사람이 골라야 하는 상태**(`needsPick`)도 ack 한다. 선택 UI 가 이미 망고
  화면에 떠 있는데 지우지 않으면, 창을 옮길 때마다 같은 UI 가 다시 뜬다.
- **한 번에 한 건만** 처리한다. 반영에 성공하면 망고가 `[선택수정]` 으로 페이지를 다시 읽어
  목록이 통째로 바뀐다. 이어서 두 번째를 밀어 넣으면 바뀐 목록 위에서 매칭하게 된다.
- 6시간이 지난 건은 버린다. 브라우저를 며칠 안 켠 뒤 뒤늦게 반영되면 곤란하다.
- 넘어온 값은 `url`·`orderNo`·`price`·`payDate`·`receiver` 가 다 있는지 확인하고 받는다.
  루프백이라도 아무거나 큐에 쌓이면 결국 망고에 그대로 써진다.

## 참고 — 확인된 제약

### 공통

- **롯데온·SSG·패션플러스는 결제 시각이 없고 날짜만** 얻을 수 있다 (`2026.08.27`). 무신사는 영수증에서
  `2026-08-28 10:03:46`, 네이버페이는 주문상세 화면에서 `2026.08.26 08:24:52` 로 시각까지 들어간다.

### 롯데온

- 주문상세에 결제 시각이 없다. 시간까지 필요하면 롯데온 내부 API 호출이 필요한데,
  Imperva 봇탐지에 걸릴 위험이 있어 채택하지 않았다.
- 결제수단이 여러 개(예: 네이버페이 + L.POINT)면 **`원` 단위 금액만 합산**하고 `P`(L.POINT)는 제외한다.

### SSG

- **전자영수증의 `발급일시` 는 결제일시가 아니다.** 영수증을 뽑은 시각이라 누를 때마다 지금 시각이
  찍힌다 (주문 2026-08-27, 발급일시 2026-08-30 15:51:23). 영수증 결제내역의 `승인일시` 도
  `2026/08/27` 로 날짜뿐이다. 그래서 영수증을 아예 열지 않고, 주문상세 상단의 주문일자를 쓴다.
  - 영수증 팝업 주소는 `pay.ssg.com/myssg/showReceiptPopup.ssg?orordNo=<주문번호>` 로 규칙적이라
    필요해지면 fetch 로 바로 읽을 수 있다.
- 주문번호 표기가 세 군데 다 다르다 — 화면 `20260827-61F020`, URL `2026082761F020`,
  영수증 `2026-08-27-61F020`. 망고에는 **화면 표기**를 넣고, 버튼 위치를 찾을 때는
  하이픈을 떼고 URL 값과 대조한다.
- 주문일자는 주문번호 앞 8자리(`YYYYMMDD`)와 같다. 화면에서 날짜를 못 찾으면 여기서 유도한다.
- 수령인 라벨이 `받는 분` 이 아니라 **`받으시는 분`** 이고, 값에 전화번호와 괄호주석이
  붙는다 (`양은영 010-2977-8032 (안심번호 사용안함)`). 숫자·괄호가 나오는 지점에서 자른다.
- 구입금액은 `총 결제금액`(30,253원)을 쓴다. SSG MONEY 로 결제한 몫(635원)은 이미 빠져 있어
  롯데온에서 L.POINT 를 제외하는 규칙과 결이 같다. 상품 자체 가격(30,888원)이 아니다.

### 무신사

- **영수증 화면이 PG사마다 다르다.**
  - 페이코 결제 → `pay.musinsapayments.com/mps/receipt/...` 가 HTML 로 다 내려준다.
    라벨이 `승인`, 값이 `2026-08-28 10:03:46`.
  - 무신사페이 결제 → 위 주소에서 `dashboard.tosspayments.com/receipt/sales-slip?...` 로
    넘어가고, 값을 **자바스크립트로 그린다**(HTML 만 받으면 날짜가 없다). 라벨도 `승인` 이 아니라
    `결제일시` 다.

  그래서 영수증은 fetch 로 파싱하지 않고 **background 가 백그라운드 탭으로 실제로 띄워
  읽고 닫는다**. 두 화면 모두 같은 정규식 하나로 잡힌다 (`승인일시|결제일시|승인` 뒤의
  `YYYY-MM-DD HH:MM(:SS)`). `승인번호` 뒤에는 숫자가 바로 붙어서 날짜 패턴에 걸리지 않는다.
  - content script 는 CORS 때문에 애초에 이 주소를 `fetch` 할 수 없다 (`Failed to fetch`).
  - 페이코 영수증 HTML 에는 **주석 처리된 예시 날짜**(`2023.04.08 22:42:17`)가 들어 있다.
    `innerText` 로 읽으므로 주석은 보이지 않지만, HTML 을 직접 정규식으로 훑는다면 이걸 조심할 것.
- 영수증을 못 읽으면 **거래명세서**(`/order-service/my/order/payment_receipt/<주문번호>`)의
  `주문 일자` 로 떨어진다. 같은 오리진 + 서버렌더라 그냥 `fetch` 로 읽힌다. 다만 **분 단위**이고
  점으로 찍혀 있어(`2026.08.27 08:32`) 영수증 표기에 맞춰 `-` 로 바꾼다. 그것도 실패하면
  주문 API 의 `orderDatetime`.
- 화면 값은 `/order-service/my/order/get_order_view/<주문번호>` JSON 에서 온다. 수령인은
  `orderInfo.r_nm`. 화면에는 수령인 라벨이 없어서(이름·주소·전화번호가 그냥 나열된다)
  DOM 으로는 안정적으로 못 뽑는다 — 이 값은 API 가 유일한 출처다.
- **즉시 할인가**는 카드사 즉시할인이 빠진 실제 청구액이다 (결제 금액 74,870 → 즉시 할인가 71,870).
  화면의 `결제 정보` 블록에서 라벨로 읽고, 블록을 못 찾으면 API 로 같은 규칙을 재현한다 —
  `promotion_discount_amt > 0` 이면 `without_recv_amt_promotion_discount_amt`, 아니면 `recv_amt`.
  두 경로가 같은 값을 내는 것을 확인했다.
  - `결제 금액` 줄에는 할인율 배지(`63%`)가 끼어 있다. 라벨 뒤 **`원` 이 붙은 첫 숫자**를 집는다.
- **SPA 다.** 주문목록에서 주문상세로 문서를 다시 읽지 않고 넘어간다. 그래서 무신사·네이버페이는
  `mount({ watch: true })` 로 붙는다 (아래 참고).
- 클래스 이름이 스타일드컴포넌트 해시(`PaymentInfo__PriceWrap-sc-7uk9xp-3`)라 빌드마다 바뀐다.
  선택자로 쓰지 않고 **한글 라벨 텍스트**로 찾는다.

### 네이버페이

- **`orders.pay.naver.com` 은 브라우저 자동화 도구로 열 수 없다** (SSG 와 같은 사정).
  그래서 화면 구조는 스크린샷으로 확인했고, 추출 로직은 그 화면 텍스트를 그대로 재현한
  가짜 DOM 에 `naver.js` 를 태워 검증했다. 값을 못 찾으면 오류 토스트에 결제정보 블록과
  배송지 주변 텍스트를 같이 실어 보낸다(`probe`) — 화면을 직접 볼 수 없을 때 원인을 좁히기 위한 것.
- **구입금액은 카드로 결제한 금액만** 쓴다. 네이버페이는 포인트를 섞어 결제하는 게 기본이라
  주문금액과 카드 청구액이 다르다 (주문금액 41,800 = 포인트 1,087 + 카드 간편결제 40,713 → **40,713**).
  롯데온에서 L.POINT 를, SSG 에서 SSG MONEY 를 빼는 규칙과 결이 같다.
  - 결제수단 줄을 고를 때 `카드` 가 들어가도 금액 줄이 아닌 것들을 걸러낸다 —
    마스킹된 카드번호(`현대 5165 **** **** ****`), 안내 문구(`무이자 … 카드사로 문의하시면`),
    할인 줄. 카드 두 장으로 나눠 결제했으면 둘 다 더한다.
- **결제일시는 주문번호 바로 위**에 `2026.08.26. 08:24:52` 로 찍혀 있다. 날짜 끝의 점만 떼고
  `2026.08.26 08:24:52` 로 넣는다. 주문번호 요소에서 위로 올라가며 찾으므로, 페이지 다른 곳의
  날짜(구매확정 예정일 등)를 집지 않는다.
- 수령인은 배송지 첫 줄인데 **배송지 별칭이 괄호로 붙는다** (`함용녀(집)`). 괄호부터 잘라낸다.
- **SPA 다.** 무신사와 같은 이유로 `mount({ watch: true })` 로 붙고, `anchor()` 는 찾은 요소를 캐시한다.
- 클래스 이름을 선택자로 쓰지 않고 한글 라벨 텍스트로 찾는다 (무신사와 같은 이유).

### 패션플러스

- **값이 전부 `<th>라벨 / <td>값` 표에 들어 있다.** 롯데온·SSG 처럼 본문 텍스트를 정규식으로
  훑지 않고 표를 라벨로 읽는다. 라벨 문구가 겹쳐도(주문자 정보·배송지 정보에 **`주문자명`이 둘 다**
  있다) 어느 표인지로 갈리기 때문에, 표를 그 위 제목(`결제수단 정보` / `배송지 정보`)으로 먼저 고른다.
- **수령인 라벨이 `받는 분`이 아니라 `주문자명`이다.** 주문자 정보의 주문자명(구매자)이 아니라
  **배송지 정보의 주문자명**을 쓴다. 값 칸에 `배송지 변경` 링크가 이름 뒤에 붙어 있어서
  (`서미경 배송지 변경`) 읽기 전에 `a`·`button` 을 걷어낸다.
- **구입금액·결제일시는 `결제수단 정보` 표에서** 가져온다 — `결제금액 44,700원`,
  `결제승인일 2026-08-29`. 위쪽 `최종 결제금액` 블록의 총 결제 예상금액은 같은 값이지만
  결제수단이 아니라 주문 기준이라, 망고 행 매칭 보조키(`total`)로만 쓴다.
  - 결제수단이 나뉘어 있으면 `결제금액` 줄이 여러 개일 수 있어 전부 더한다.
  - `총 결제 예상금액(1건)44,700` 처럼 금액 앞에 **`(1건)` 이 붙어** 있다. 괄호를 건너뛰지 않으면
    건수의 `1` 을 금액으로 집는다.
- 결제승인일은 `2026-08-29` 로 하이픈 표기다. 롯데온·SSG 와 맞춰 `2026.08.29` 로 바꿔 넣는다.
- **발주처 태그(`marketTag`)가 없다.** 망고 목록의 발주처 표기는 그 주문건을 어디서 사왔는지가
  아니라 망고에 등록된 공급처라, 패션플러스에서 산 건도 `[LOTTEON.com]` 으로 찍혀 있었다.
  잘못된 태그는 매칭 점수(+2)를 영영 못 받을 뿐이라 아예 넘기지 않는다. 실제로 찍히는 표기가
  있으면 `extract()` 반환값에 `marketTag` 한 줄만 추가하면 된다.
- 주문번호는 URL 경로에서 읽는다 (`/mypage/order/detail/141324230`). 화면 제목 줄에도
  같은 번호가 `141324230 (신청일: 2026-08-29)` 로 찍혀 있어 그 옆이 버튼 자리다.
- **Vue 가 우리 버튼을 죽은 껍데기로 다시 그린다.** SPA 는 아니지만 `mount({ watch: true })`
  로 붙는 이유다.
  - 주문상세 영역(`#my_order_detail`)에 **Vue 2.6.12 가 마운트**한다. `el` 만 주고 `render`
    함수가 없으면 Vue 2 는 **그 요소의 기존 DOM 을 템플릿으로 컴파일해 새로 그린 뒤 통째로
    교체**한다. `document_idle` 에 먼저 붙은 우리 버튼도 그 템플릿에 섞여 들어가,
    **마크업·CSS 는 똑같은데 클릭 리스너만 없는 복제본**으로 다시 태어난다.
  - 증상이 고약하다 — 버튼은 멀쩡히 보이는데 **눌러도 아무 일도 일어나지 않는다.** 토스트도,
    `전송 중…` 라벨 변화도 없다. 확장 오류가 아니라 리스너가 애초에 없는 것이라 콘솔도 조용하다.
  - 확인 방법: `getComputedStyle`·`elementFromPoint`·이벤트 전파는 전부 정상인데
    `버튼.click()` 조차 무반응이면 이 경우다. 마운트가 끝난 뒤 같은 자리에 손으로 붙인
    버튼은 정상 동작한다. `조상요소.__vue__` 로 어디에 마운트했는지 알 수 있다
    (단, `__vue__` 는 MAIN 월드 속성이라 content script 에서는 안 보인다).
  - 대응은 `watch: true` 다. 옵저버가 살아 있으니 Vue 가 다시 그린 직후 틱에 진짜 버튼을
    다시 붙인다. 남아 있는 껍데기는 `common.js` 의 `place()` 가 걷어낸다 — 붙이기 직전에
    `#lm-send-btn` 중 자기 자신이 아닌 것을 지운다.

### 망고

- 망고 목록 페이지는 `Array.prototype.find`가 정상 동작하지 않는다. 확장은 격리된 컨텍스트에서

### 마켓 추가하기

`common.js` 가 버튼·토스트·전송을 다 맡으므로, 사이트 스크립트는 두 가지만 내놓으면 된다.

```js
window.__LM_SITE__.mount({
  extract, // () => { url, orderNo, price, payDate, receiver, total, marketTag } | { error }
  anchor,  // () => 버튼을 옆에 붙일 요소 (없으면 우측 하단 고정 버튼으로 폴백)
  watch,   // (선택) SPA 면 true — 라우트가 바뀌어도 버튼을 따라 붙인다
});
```

`marketTag` 는 문자열 또는 배열이다.

#### `watch` — SPA 대응

무신사·네이버페이는 주문목록에서 주문상세로 **문서를 다시 읽지 않는다**. content script 는 그때
다시 주입되지 않으므로, 버튼을 한 번 붙이고 끝내면 라우트가 바뀌는 순간 사라진다.

`watch` 는 SPA 전용이 아니다. 패션플러스처럼 **페이지가 우리 버튼을 통째로 다시 그리는**
경우(Vue 마운트)도 같은 장치로 잡는다 — 버튼이 갈려 나갔다는 사실은 둘 다 똑같기 때문이다.

`watch: true` 면 `MutationObserver` 를 끊지 않고(여전히 150ms 에 한 번) 매 틱마다

- `anchor()` 가 요소를 주면 그 옆에 (이미 그 자리면 아무것도 안 하고) 붙이고,
- `null` 을 주면 — 주문상세가 아닌 화면이라는 뜻이라 — 버튼을 떼어낸다.

매 틱 `anchor()` 를 부르므로 **캐시는 사이트 스크립트 몫이다.** `musinsa.js`·`naver.js`·`fashionplus.js` 는 찾은 요소를
들고 있다가 `isConnected` 와 현재 주문번호만 확인하고 돌려준다. 캐시가 살아 있는 동안
문서를 훑는 비용은 0이고, 라우트가 바뀐 틱에만 `TreeWalker` 로 다시 찾는다.

`extract` 는 `await` 되므로 비동기여도 된다. 새 사이트는 `manifest.json` 의
`host_permissions` 와 `content_scripts` 에 한 줄씩 추가하면 끝이다.
